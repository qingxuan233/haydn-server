# 18 · 控制台补齐、项目持久化与容器运行环境优化方案

> 基于 2026-11-10 的实测与踩坑经验（docs/08、09、13、17）给出**方案设计**，不是本次立即执行的变更清单。
> 目标：让这台"研究平台"更完整、更可恢复、更省资源；所有方案都标明优先级/风险/验收方式。

### 1.1 控制台 v2 已有能力（docs/13）

### 1.2 控制台未完成/薄弱点

| # | 缺口 | 现状证据 | 影响 | 优先级 |

## 3. 方案 A：控制台补齐

### 3.1 A0 状态持久化（SQLite，P0）

**为什么**：`console-api.py` 是零依赖 stdlib 服务，进程重启/看门狗重启后历史全丢；SQLite 在 stdlib 内（`sqlite3`），零外部依赖，符合"手机端轻量"。

- 数据库：`/root/server/state/console.db`（WAL，文件权限 600，目录 700）；纳入 `server-backup`。
- 表结构（建议）：

```sql
CREATE TABLE samples(
  ts INTEGER PRIMARY KEY, cpu_pct REAL, mem_used_pct REAL,
  mem_available_mb INTEGER, disk_free_gb REAL, temperature_c REAL,
  battery_level INTEGER, net_rx_kbps REAL, net_tx_kbps REAL
);
CREATE TABLE service_events(ts INTEGER, service TEXT, event TEXT, detail TEXT);
CREATE TABLE audits(ts INTEGER, actor TEXT DEFAULT 'admin', action TEXT,
  service TEXT, ip TEXT, proto TEXT, ok INTEGER, detail TEXT);
CREATE TABLE backups(ts INTEGER, name TEXT PRIMARY KEY, size INTEGER,
  sha256 TEXT, verified INTEGER DEFAULT 0, offsite INTEGER DEFAULT 0);
CREATE TABLE settings(key TEXT PRIMARY KEY, value TEXT);
CREATE TABLE alerts(id INTEGER PRIMARY KEY, ts INTEGER, level TEXT,
  key TEXT, message TEXT, delivered INTEGER DEFAULT 0);
```

- 采样写入：sampler 每 10s 写 `samples`（后续可调到 30s）；保留策略：原始 7 天、1 分钟粒度 30 天、1 小时粒度 1 年（后台每小时聚合）。
- API v3（保留 v2 兼容）：
  - `GET /api/v3/history?range=1h|24h|7d`（按范围降采样返回）
  - `GET /api/v3/audit?limit=100`（审计查询，需 token）
  - `GET /api/v3/backups`（含 sha/verify/offsite 状态）
  - `GET /api/v3/health`（DB 可写、sampler 存活、服务数）
- 降级：DB 打不开 → 退回现有 JSONL/内存环，并在页面提示"历史存储降级"。
- 验收：重启 API 后 24h 曲线仍存在；DB 文件出现在备份包内；`PRAGMA integrity_check=ok`。

### 3.2 A1 备份闭环（P0）

1. **校验**：`server-backup --verify-last`：解密 → `tar tzf` → `sqlite3 integrity_check` → 生成 manifest（sha256/大小/内容清单）写入 `backups` 表。
2. **恢复**：只提供 CLI（`server-restore --from <file> --target <dir> --yes`）+ 网页展示"恢复步骤/校验状态"，**不做网页一键恢复**（避免误操作毁服务器）。
3. **保留**：设备 7 份、PC 30 份、异地 12 份；`server-backup` 增加 `--keep` 参数化。
4. **异地**：见方案 B（同步/拉取）。
5. 验收：模拟删除一个服务配置后从备份恢复到临时目录并 diff；记录 RTO。

### 3.3 A2 告警与外部门铃（P1，关键）

- **手机自身宕机时，机内告警无意义** → 必须"外部门铃"：
  - 在 PC/云上跑 Uptime Kuma（或最小 cron+curl），探测 `http://47.97.70.99:48108/health`、`https://.../health`、SSH 端口、DSH `/app-login`。
  - 控制台提供 `GET /api/heartbeat`（供外部推送/拉取）和反向 **push heartbeat** 到 Uptime Kuma Push URL（可选）。
- 机内告警：`alerts` 表 + 投递队列；规则：
  - 服务 down 连续 2 次；磁盘 <10%；温度 >50℃；证书 <14 天；备份失败；DB 写入失败。
- 通道优先级：ntfy/Bark/Telegram Bot（HTTP，简单）→ SMTP（可选）→ 企业微信/Webhook。
- 去重窗口 10 分钟；失败重试指数退避；`delivered` 状态可查。

### 3.4 A3 日志与状态（P1）

- `GET /api/v3/logs/stream?name=`（SSE，按行推送，前端"自动跟随"）。
- 服务端关键字过滤/忽略 ANSI；`GET /api/v3/logs/rotate-status`（各日志大小/最后轮转）。
- 下载当前日志（gzip）与"最近 3 份轮转"列表。

### 3.5 A4 服务生命周期（P1）

- `services.d/*.json` 增加：`depends_on`（如 nginx→api/gitea/dsh；frpc→nginx；dsh-login→dsh）、`maintenance` 开关、`validate_cmd`（nginx `-t`）。
- 重启按依赖逆序；维护模式暂停自动恢复；操作前校验配置、操作后健康检查，失败自动回滚到旧配置快照。
- 所有动作写审计（已有）。

### 3.6 A5 权限/会话（P2）

- 保留 `X-Console-Token` API 模式；UI 增加可选登录会话（`HttpOnly; Secure; SameSite=Lax` Cookie + CSRF token），支持令牌轮换按钮（写审计）；按 IP 限流（已有每秒 1 次，可加突发桶）。
- 角色：`admin`/`viewer`（viewer 只读指标/日志，不可动作）。

### 3.7 A6 测试与验收

- 单进程 API 契约测试（stdlib `unittest`）：路由 200/401/403/429；token 对比恒定时间；日志/备份/动作。
- 持久化测试：重启 API 后历史/审计仍在。
- 告警测试：停掉 api 服务 2 次检查 → 触发告警投递记录。
- 验收指标：API P95 < 1s；页面首屏 < 2s；重启后历史可见。

## 4. 方案 B：项目持久化（3-2-1）

### 4.1 资产分层与目标策略

| 层 | 资产 | 频率 | 方式 | 目标 |
|---|---|---|---|---|
| L0 设备主副本 | `/root/server` + `/root/.dsh/profiles` + `state/console.db` + vault/token | 实时 | 正常运行 | 主数据 |
| L1 设备内备份 | `/root/server/backups`（加密 `.tar.gz.enc`） | 每日 03:00 | `server-backup` + verify | 防误删/回滚 |
| L2 PC 副本 | 上述备份 + `server-manifest.json` | 每日/每周 | PC 脚本 `scp`/`adb pull` | 异地机器副本 |
| L3 异地副本 | 加密备份 + manifest + rootfs base | 每日/每周 | Syncthing 到 PC/远程；或 rclone 到 WebDAV/S3 | 一台设备毁掉仍可恢复 |
| L4 代码/文档 | Git 仓库 | 每次变更 | git commit/push | 环境即代码 |

### 4.2 关键缺口修复

1. **把 DSH profile 纳入备份**：`/root/.dsh/profiles/server`（及 `~/.dsh` 必要配置），排除 cache/临时/会话可重建内容；先测体积/内容再定 tar 规则（286MB 中可能包含 workspace/cache）。
2. **把 console state DB 纳入备份**（方案 A0）；`server-backup` 对 sqlite 用 `.backup` 快照。
3. **把 Syncthing 数据目录**（如 `/root/Sync`）按"用户数据"分类：加入备份或明确排除（并在文档声明）。
4. **PC 拉取脚本** `scripts/backup-pull.ps1`：通过 SSH 拉取最新 N 个加密备份 + manifest；失败告警。
5. **异地同步**：
   - 首选 Syncthing：手机 `/root/server/backups` → PC/另一台设备（**公网 relays 已启用**）；加密文件可安全传输。
   - 备选 rclone（WebDAV/S3）——手机上 apt 安装 rclone，定时上传；带宽/电量需评估。
6. **manifest 与环境清单**：`server-manifest.json`（服务列表/端口/版本/校验和/备份策略/rootfs base hash）；恢复时先校验 manifest。
7. **恢复演练**：每月 `--verify`，每季度在临时目录实际解包+启动只读校验；记录 RTO。

### 4.3 RPO/RTO 建议

| 场景 | RPO | RTO | 手段 |
|---|---|---|---|
| 服务配置误改 | ≤24h（或手动立即备份） | 10–30min | 每日备份 + L1 |
| 设备丢失/损坏 | ≤24h | 1–2h | L2/L3 + docs/17 重建 |
| 全盘重置（恢复出厂） | ≤24h | 2–4h | L3 + rootfs base + APK/物料 |
| 代码/文档丢失 | ≈0 | 分钟级 | Git |

### 4.4 rootfs/Termux 持久化

- **不做每日全量 rootfs 备份**（体积/IO 不划算）；策略：
  - 固定 `ubuntu-base.tar.gz`（已存档）+ `apt/versions manifest`；
  - 变更较大时（装新服务/升级）生成 **差异快照**（`rsync --link-dest` 或 `tar --newer` 到 PC）；
  - 定期导出 Termux 侧脚本（`ubuntu.sh`、`.termux/boot/00-server.sh`、`termux-metrics.sh`）到仓库/PC。
- 恢复顺序：Android 基础 → Termux/proot → rootfs base → server 备份 → DSH profile → 验证脚本（docs/17）。

## 5. 方案 C：容器运行环境优化

### 5.1 目标

- proot CPU：18.9% → **≤15–18%**（不牺牲可靠性）；
- DSH RSS：421MB → **≤350MB**（DevTools 关闭、heap 限制）；
- 启动：≤45s；内存可用 ≥4.2G；无新增故障；
- 方法：先测量、后单变量变更、可回滚。

### 5.2 优化项清单

| ID | 措施 | 预期收益 | 风险/代价 | 验证 |
|---|---|---|---|---|
| O1 | **看门狗迁到 Termux**：用 Termux `curl` 直接调用 supervisor **XML-RPC**（127.0.0.1:9001），不再每 180s spawn proot 进程 | 显著降 proot CPU（减少 fork/exec/PTRACE） | 需实现/测试；supervisor 端口/认证暴露仅本机 | A/B `dumpsys cpuinfo` 的 proot% |
| O2 | 采样间隔 10s→30s，控制台 DB 写入降频；metrics JSONL 保留 | 降 proot/Python CPU 与 IO | 图表分辨率下降（可接受） | API P95/CPU |
| O3 | DSH `--max-old-space-size=512`（A/B），关闭 DevTools 会话 | RSS/CPU 下降 | 极限负载可能 OOM（观察） | `ps` RSS + 功能测试 |
| O4 | 日志/TMP 移到 `/hosthome`（`TMPDIR`、nginx 日志可选） | 减少 rootfs 写，备份更小 | 路径兼容/备份脚本调整 | 写压测 + diff |
| O5 | proot 最小绑定实验（去掉不必要的 fd 绑定；仅保留服务需要的） | 减少 syscall 拦截 | 服务兼容性风险 | 逐服务验证 + 回滚 |
| O6 | 服务瘦身：评估 fileui 是否可由 nginx autoindex + Basic Auth 替代；api/fileui 是否合并 | 少一个 Python 进程与端口 | 功能缺失/体验变化 | 功能清单对照 |
| O7 | supervisord 参数：`autorestart=unexpected`、`startsecs`、`stopwaitsecs` 调整；启动顺序 | 减少无谓重启/加快启动 | 故障恢复策略变化 | 故障注入测试 |
| O8 | nginx 微调（worker_connections、open_file_cache、keepalive、gzip/缓存已做） | 并发/首屏小幅提升 | 低 | TTFB/并发测试 |
| O9 | Android 宿主：Termux 白名单/唤醒锁复核、屏幕常熄、蓝牙/扫描关闭 | 稳定性 | 已基本完成 | `phone-health` |
| O10 | 长期：外部 exporter（Prometheus/node_exporter?）不适合 proot；用 API 导出 | 可观测性 | 额外服务 | 外部监控 |

> 不可做（无 Root）：CPU governor/频率、I/O scheduler、zram/swap、cgroup 限制、内核参数、真正隔离。

### 5.3 O1 具体做法（最值得做）

- supervisord 已配置 `inet_http_server`（`supervisorctl` 通过 127.0.0.1:9001 + user/pass）。
- Termux 与 proot 共享同一个 Android 网络命名空间，因此 Termux 侧可直接 `curl http://127.0.0.1:9001/RPC2` 调用 XML-RPC：
  - `supervisor.getState` / `getAllProcessInfo` / `startProcess` / `stopProcess`。
- Termux 侧用 `curl` + 小型 bash/awk 解析即可实现轻量看门狗（或离线安装 Termux `python` 的 deb，若需要更好 XML 处理）。
- 仅在"需要重启服务"时才进入 proot（甚至不需要：supervisor RPC 可直接 restart）。
- 收益预估：可去掉每 180s 多次 `supervisorctl`/`curl` 的 fork/exec；proot CPU 有希望再降 2–5 个百分点（以实测为准）。

### 5.4 A/B 测量协议

1. 基线 10 分钟（同一时段、无 DevTools、屏幕熄灭）：`dumpsys cpuinfo` proot/node、`/api/sysinfo`、TTFB、`free`。
2. 单变量变更 → 再测 10 分钟；保留原始日志。
3. 验收阈值：proot ≤18%、node ≤5%、TTFB 不退化、重启 ≤45s、24h 无看门狗重启。
4. 回滚：脚本/配置均有备份；变更前记录 `supervisord.conf`/`nginx`/`server-watch` 快照。

## 7. 验收指标（汇总）

- 控制台：重启后 24h 历史可查；审计/备份校验可见；API v3 P95 <1s。
- 备份：最近一份可 `--verify` 通过；PC/异地各有一份；恢复演练 RTO ≤1h。
- 告警：人为停 api 2 个周期 → 告警投递成功；手机关机时外部门铃能报警。
- 容器：proot CPU ≤18%（目标 15–18%）；DSH RSS ≤350MB；重启 ≤45s；11/11 服务；24h 无重启。
- 安全：管理 token 不泄露；公网 HTTP 只读；备份加密；端口最小化。
