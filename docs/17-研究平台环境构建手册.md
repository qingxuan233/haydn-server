# 17 · 研究平台环境构建手册（Reproducible Research Environment）

> 定位：这台 Redmi K40 Pro 是**研究/方案验证平台**。本手册的目标不是"把这台机器修好"，而是：
> **任何人/任何一次重置后，都能按同样流程重建这套环境，并理解每一步为什么这样做、踩过什么坑。**
>
> 范围：Android 宿主 → Termux → proot Ubuntu → Linux 服务器栈 → DSH → Android 深度研究工具（Shizuku/AppManager/Canta/Hail/UAD）。
> 适用：无 Root、Bootloader 锁定、HyperOS 1.0（CN）、Android 14。

---

## 1. 环境架构

```text
PC (Windows, PowerShell 5.1)
 │  adb / 脚本 / 下载镜像 / 备份
 ▼
Redmi K40 Pro (Android 14, HyperOS 1.0 CN, BL locked)
 │  开发者选项：USB 调试 + USB 调试（安全设置）
 │  Termux (com.termux) + Termux:Boot
 │      └─ proot (离线安装) ──► Ubuntu 24.04 arm64 rootfs (~/ubuntu)
 │             └─ supervisord
 │                  ├─ nginx (8080 / 8443 TLS)
 │                  ├─ gitea (127.0.0.1:3000)
 │                  ├─ syncthing (8384)
 │                  ├─ webdav (8083) / fileui (8085) / api (8000)
 │                  ├─ sshd (127.0.0.1:2222)
 │                  ├─ frpc ──► 公网 frps 47.97.70.99（48104 / 44904 / 13872）
 │                  ├─ dsh (Node24, 127.0.0.1:3081；对外 /app/)
 │                  ├─ dsh-login (127.0.0.1:3082，稳定登录入口)
 │                  └─ runner（Gitea Runner）
 │  研究 App：Shizuku / Canta / Hail / AppManager（AppOps/冻结/卸载/权限）
 │  UAD-NG 清单（只读比对）
 └─ 直接 ADB 通道：USB 串口 2b3be151 或 WiFi adb:5555；proot 内自建 ADB 可控制自身
```

**为什么是这套结构：**
- 内核缺 `CONFIG_USER_NS/PID_NS` → Docker/容器不可用；只能 proot。
- 无 Root、BL 锁定 → 不能刷内核/Magisk/KernelSU；systemd 也不可用 → supervisord。
- HyperOS 限制 adb 安装与系统包卸载 → 安装走 UI 自动化；后台治理走 appops/suspend。
- Android 13+ FBE：锁屏凭据会让 BOOT_COMPLETED 延迟 → 研究机保持**无锁屏凭据**，实现无人值守自启。

## 3. 从零复现流程（Phase 0–6）

### Phase 0 · PC 侧准备

1. 安装 Platform Tools，确认 `adb devices` 能识别；首次授权时手机弹窗选「始终允许」。
2. 准备 PowerShell 5.1（Windows 自带）；**所有含中文的 .ps1 需保存为 UTF-8 BOM**，否则会乱码/解析失败。
3. 网络镜像（可选但强烈建议）：
   - Termux 包索引 `https://packages.termux.dev/apt/termux-main/dists/stable/main/binary-aarch64/Packages.gz`
   - Ubuntu 源 TUNA `https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports`
   - Node `https://mirrors.tuna.tsinghua.edu.cn/nodejs-release/`
   - APK 代理 `https://ghfast.top/` + 原 GitHub URL
   - UAD 清单 `https://cdn.jsdelivr.net/gh/Universal-Debloater-Alliance/.../uad_lists.json`
4. 屏幕保持唤醒（自动化点按需要）：`adb shell "settings put system screen_off_timeout 1800000"`，结束恢复 15000。

### Phase 1 · Android 基础环境

1. 开发者选项：开启 **USB 调试** 和 **USB 调试（安全设置）**（MIUI 第二个开关；缺它会导致 ADB 权限受限）。
2. 研究机保持 **无锁屏凭据**（PIN/图案/密码 = 无）→ FBE 开机即解密，Termux:Boot 可无人值守触发。
3. 安装 Termux 与 Termux:Boot（**MIUI 会拦截 adb install**，用脚本自动点「继续安装」）：
   ```powershell
   powershell -File scripts\miui-adb-install.ps1 -Apk tools\termux\termux-app-arm64.apk
   powershell -File scripts\miui-adb-install.ps1 -Apk tools\termux-boot\termux-boot.apk
   ```
4. 启动 Termux 一次，确认 bootstrap 已解包（`run-as com.termux ls $PREFIX/bin | wc -l` ≈389）；授予存储权限。
5. 保活（重启后失效，需重做）：
   ```bash
   adb shell cmd deviceidle whitelist +com.termux
   adb shell cmd appops set com.termux RUN_ANY_IN_BACKGROUND allow
   ```
6. 研究 App（可选）：Shizuku / Canta / Hail / AppManager 均用 `miui-adb-install.ps1` 安装；Shizuku 用 §5 的启动方式。

### Phase 2 · Termux 侧：proot 离线安装 + rootfs

> 经验：Termux 的 `pkg install proot` 在慢网络下会卡死并持有 dpkg 锁 → **改为 PC 解包 .deb 离线安装**。

1. 下载并解析 Termux `Packages.gz`（PC）：
   - 获取 `proot` / `libtalloc` / `libandroid-shmem` 三个 `.deb` 的 `Filename`；
   - 实测版本：`proot_5.1.107.102_aarch64.deb`、`libtalloc_2.5.0_aarch64.deb`、`libandroid-shmem_0.7_aarch64.deb`。
2. PC 解包 `.deb`（ar + data.tar.xz），得到：
   - `bin/proot`
   - `libexec/proot/loader`, `loader32`
   - `lib/libtalloc.so.2.5.0`、`lib/libandroid-shmem.so`
3. 推送到手机并安装到 Termux 前缀：
   ```bash
   adb push proot-offline /data/local/tmp/proot-offline
   adb shell 'run-as com.termux sh /data/local/tmp/install-proot.sh'
   ```
   目标：`$PREFIX/bin/proot`（755）、`$PREFIX/libexec/proot/loader`、`$PREFIX/lib/libtalloc.so.2*`、`$PREFIX/lib/libandroid-shmem.so`；`proot --version` 能输出版本横幅。
4. 推送 `ubuntu-base.tar.gz`，在 Termux 内解包到 `~/ubuntu`（`tar --no-same-owner`；设备节点缺失可忽略）：
   ```bash
   mkdir -p ~/ubuntu
   tar --no-same-owner -xzf /data/local/tmp/ubuntu-base.tar.gz -C ~/ubuntu
   ```
5. 创建 `~/ubuntu.sh`（核心：**不绑定 `/sdcard`**，否则 proot 会触发 `compare_paths2 assertion` → SIGABRT；rootfs 内用 `/sdcard -> /hosthome/sdcard` 软链）：
   - 绑定 `/dev /proc /sys`、`/proc/self/fd`、`$HOME:/hosthome`
   - `PROOT_NO_SECCOMP=1`，`-0`，`--kill-on-exit --link2symlink`
   - 入口 `/lib/ld-linux-aarch64.so.1 /usr/bin/env -i ... /bin/bash -lc "$*"`
   （完整脚本见 `scripts/server/ubuntu.sh`）
6. 创建 `~/.termux/boot/00-server.sh`：`termux-wake-lock` → `ubuntu.sh 'server-up; exec server-watch'`（见 `scripts/server/00-server.sh`）。

### Phase 3 · Ubuntu 与服务器恢复

1. 解包服务器数据备份到 rootfs：
   ```bash
   tar --no-same-owner -xzf /data/local/tmp/a-route.tgz -C ~/ubuntu   # 含 /root 与 /etc
   ```
2. 修 DNS（Ubuntu 24.04 的 `/etc/resolv.conf` 常是指向不存在 systemd stub 的坏软链）：
   ```bash
   rm -f /etc/resolv.conf
   printf 'nameserver 223.5.5.5\nnameserver 119.29.29.29\n' > /etc/resolv.conf
   ```
3. apt 源统一 TUNA `ubuntu-ports`；禁用/备份冲突的 `ubuntu.sources`；`apt-get update`。
4. 安装服务依赖（无 systemd 的坑：`policy-rc.d` 返回 101，`systemctl` shim）：
   ```bash
   printf '#!/bin/sh\nexit 101\n' > /usr/sbin/policy-rc.d && chmod 755 /usr/sbin/policy-rc.d
   printf '#!/bin/sh\nexit 0\n' > /usr/local/bin/systemctl && chmod 755 /usr/local/bin/systemctl
   DEBIAN_FRONTEND=noninteractive apt-get install -y \
     nginx supervisor openssh-server python3 python3-pip syncthing git ca-certificates curl procps psmisc logrotate
   ```
5. Python 依赖：`pip3 install --break-system-packages --ignore-installed wsgidav cheroot`（避开 Debian 安装的 blinker 冲突）。
6. sshd：`ssh-keygen -A` + `mkdir -p /run/sshd`（否则报 Missing privilege separation directory）。
7. 启动服务器：`/root/server/bin/server-up`，确认 `supervisorctl status` 全 RUNNING；LAN 8080/8443 健康检查 200。
8. nginx 的关键配置已在备份里：8080 站点、8443 TLS（证书 `/root/server/tls/cert.pem`）、`$http_host` 保留端口；frpc 沿用原公网隧道配置。

### Phase 4 · DSH 重建

1. Node24（TUNA）：
   ```bash
   curl -fsSL -o /tmp/node.tar.xz https://mirrors.tuna.tsinghua.edu.cn/nodejs-release/v24.22.2/node-v24.22.2-linux-arm64.tar.xz
   tar -xJf /tmp/node.tar.xz -C /opt && mv /opt/node-v24.22.2-linux-arm64 /opt/node24
   ```
2. 安装 DSH：
   ```bash
   PATH=/opt/node24/bin:$PATH npm install -g --prefix /opt/dsh @deepseek-ai/dsh@0.2.2-rc.1
   cd /opt/dsh/lib/node_modules/@deepseek-ai/dsh
   npm install --no-save node-addon-require-builtin-linux-arm64-gnu@0.1.9   # 关键：npm 会跳过可选平台依赖
   ```
3. **包装器**（不要 `cat > /opt/dsh/bin/dsh`，它会穿透 symlink 覆盖 `bin.js`）：
   ```bash
   rm -f /usr/local/bin/dsh
   printf '#!/bin/sh\nexec /opt/node24/bin/node /opt/dsh/lib/node_modules/@deepseek-ai/dsh/lib/bin.js "$@"\n' > /usr/local/bin/dsh
   chmod 755 /usr/local/bin/dsh
   ```
4. supervisor `[program:dsh]`：`127.0.0.1:3081` + `--public-url https://47.97.70.99:44904/app/` + 多个 `--trusted-host`（含公网/LAN 新旧 IP）。
5. nginx `/app/` 前缀剥离反代（`proxy_pass http://dsh_upstream/`；`Host $http_host`；`proxy_set_header Origin ""`；cookie `Secure`）。
6. 辅助服务：`dsh-login`（127.0.0.1:3082，从 `dsh.log` 取当前 token 完成稳定登录）；`server-dsh`（status/url/restart）。
7. 验证：公网 `/app-login` 302、token 入口 200（40KB 页面）、静态 JS 200；token 用 `server-dsh url` 取（每次重启变化）。

### Phase 5 · Android 深度研究工具

1. **Shizuku（ADB 身份）**
   - 安装：`scripts/miui-adb-install.ps1`（MIUI 弹窗自动化）。
   - 启动（v13.6 与旧版不同，不是 start.sh）：
     ```bash
     APK=$(adb shell pm path moe.shizuku.privileged.api | sed 's/package://')
     adb shell "${APK%base.apk}lib/arm64/libshizuku.so"
     ```
     输出 `shizuku_server pid is ...`；UI 显示「正在运行（adb）」。
   - **每次重启后必须重新启动**；`scripts/shizuku-adb-start.ps1 -Start` 已封装动态路径。
2. **Canta**：Shizuku 授权后浏览 UAD 评级；**只用清单比对，不执行系统包卸载**（曾有 bootloop 前科）。
3. **Hail**：工作模式需手动切到「Shizuku - 强行停止」；Intent 冻结要求目标先加入 Hail 首页。
4. **AppManager（推荐研究工具）**
   - AppManager 自带 `librun_server.so`，无需 Shizuku：在其「设置→操作模式→自定义命令」复制命令，用 ADB 执行：
     ```bash
     /data/app/~~.../lib/arm64/librun_server.so 60001 jolly-fit-dove am.jar main.jar io.github.muntashirakon.AppManager 0 0
     ```
     然后 AppManager「操作模式→网络调试→应用」→ 显示 `ADB / 远程服务启用中 / 已通过remote service连接`。
   - 脚本：`scripts/appmanager-adb-mode.ps1 -Start/-Status/-Stop`（验证后立即 `-Stop`，避免 60001 暴露）。
5. **UAD-NG 只读比对**：`python scripts/uad-compare.py` → `inventory/uad-compare-*.md`（本机命中 339 条：Unsafe 58 / Recommended 123 / Advanced 84 / Expert 74）。

## 4. 关键设计决策（ADR 摘要）

| 决策 | 理由 | 代价/风险 |
|---|---|---|
| 用 **proot** 而非 Docker | 内核无 USER_NS/PID_NS，容器不可用 | 无隔离、ptrace 开销大（实测 proot ~19–33% 单核） |
| 用 **supervisord** 而非 systemd | proot 无 PID1/systemd 权限 | 自写看门狗/健康检查 |
| **不绑定 /sdcard** | proot 对软链 sanitize 触发 assertion → SIGABRT | 备份路径改为 `/hosthome/sdcard` |
| 服务由 **Termux App/开机脚本**上下文启动 | `run-as` 上下文（shell/SELinux）下 proot 不稳定 | 必须依赖 Termux:Boot/PC 启动 |
| 保持 **无锁屏凭据** | FBE 下 BOOT_COMPLETED 在解锁前不触发 | 设备无锁屏安全 |
| MIUI 安装走 **UI 自动化** | adb install 被 SecurityCenter `AdbInstallActivity` 拦截 | 依赖中文按钮文案/分辨率 |
| AppManager 用 **ADB 模式**而非 Shizuku | 无需 Shizuku、权限等同 shell、可脚本化 | 60001 端口暴露；重启需重启动 |
| **禁止 uninstall 系统包** | ext.services 缺失导致 system_server crash/bootloop（已发生） | 只能 disable/suspend/appops |
| 公网入口复用原 **frp 8443 /app/** | 保持既有访问路径 | token 每次重启变化；需 trusted-host |

## 5. 经验矩阵（症状 → 根因 → 处理 → 预防）

| # | 症状 | 根因 | 处理 | 预防/记录 |
|---|---|---|---|---|
| 1 | 重启后无限降级/RescueParty | 误 uninstall `com.google.android.ext.services` | 恢复出厂 + 从备份重建 | 系统包只 disable，禁止 uninstall → docs/08 |

## 8. 方法论（比步骤更重要）

1. **先探测、后修改**：`adb shell getprop`/`cmd -l`/`dpm`/`pm list users`/`device_config list` 只读摸底；每项写操作可逆。
2. **单变量原则**：一次只改 1–2 项，改完立即验证（重启/健康检查/日志），失败先回滚。
3. **证据链**：logcat、watch.log、supervisord.log、crash buffer 是判断根因的第一手材料；不要凭猜。
4. **安全红线**：系统包不卸载；不执行 `am kill-all`；不盲目用第三方"一键优化"；不在主力机尝试解锁/EDL。
5. **可复现**：所有命令进脚本、所有变更进文档、所有备份有路径；版本/来源/镜像写清楚。
6. **环境即代码**：脚本入库、配置备份、每次重建都更新手册。

## 9. 已知限制与风险

- **无 Root / BL 锁定**：不能调频、I/O 调度、zram、温度墙；不能 Magisk/KernelSU（详见 docs/16）。
- **MIUI 限制**：系统包不能 disable；appops 重启重置；安装需 UI 确认。
- **proot 税**：常驻 19–33% 单核 CPU（取决于负载与看门狗频率）；内核参数不可调。
- **公网暴露**：48104/44904/13872 对公网开放（沿用原配置）；token/Basic Auth 需管理。
- **DHCP/IP 变化**：脚本应动态取 IP；建议路由器静态租约。
- **无锁屏**：研究机的取舍；外出携带需自行评估。
