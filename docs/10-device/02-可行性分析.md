## 1. 结论先行（TL;DR）

1. **代号先确认**：K40 Pro = `haydn`；K40（非 Pro，骁龙 870 / SM8250-AC）= `alioth`。任务描述里「可能 haydn 或 alioth」是危险的混淆点——**两者 SoC 不同、社区支持状况完全不同**（alioth 有工作到一半的 Nura 移植，haydn 连设备页都没有）。**【已核实】**
   - 来源：[LineageOS Wiki /devices/haydn](https://wiki.lineageos.org/devices/haydn/)、[Nura Wiki: POCO F3 / Redmi K40 / Mi 11X (xiaomi-alioth)](https://wiki.nura.eco/wiki/Xiaomi_POCO_F3_/_Redmi_K40_/_Mi_11X_(xiaomi-alioth))
2. **原生 Linux 移植：当前不可行**。postmarketOS（现以 **Nura** 名义运营/更名，`wiki.postmarketos.org` 现已跳转到 `wiki.nura.eco`；更名公告本身未直接抓到，仅观察到域名迁移与站内命名，见 raw-notes §0）中 **没有 haydn 设备页**，Wiki 检索 `haydn` 0 结果；同 SoC 的边缘兄弟 **Mi 11 (venus) / Mi 11 Ultra (star) 均被标记 "not booting"**；SM8350 平台内核包在 pmaports 中处于 **archived**；Ubuntu Touch 无 haydn（`/device/haydn` 404）；Droidian（Debian+libhybris/Halium）无 Xiaomi 设备仓库；Mobian 只面向 PinePhone/Librem 5/OnePlus 6 等。**【已核实】**
   - 来源：[Nura Wiki SM8350 SoC 页](https://wiki.nura.eco/wiki/Qualcomm_Snapdragon_888_(SM8350))、[Mi 11 (venus)](https://wiki.nura.eco/wiki/Xiaomi_Mi_11_(xiaomi-venus))、[Mi 11 Ultra (star)](https://wiki.nura.eco/wiki/Xiaomi_Mi_11_Ultra_(xiaomi-star))、[Ubuntu Touch 设备库](https://devices.ubuntu-touch.io/)、[droidian-devices](https://github.com/droidian-devices)、[Mobian](https://mobian-project.org/)
3. **不 root 的唯一完整 Linux 路线 = Termux + proot-distro（A 路线）**：proot 是用户态 `chroot + mount --bind + binfmt_misc` 的 ptrace 实现，**不需要 root**；2026 版的 proot-distro 直接从 OCI 镜像装 Ubuntu/Debian/Alpine（`proot-distro install ubuntu:24.04`）。但它**官方明示**：无真 root（`iptables`/`mount` 失败）、**无 cgroups/namespaces**、**无后台服务 systemd/OpenRC**、ptrace 带来明显 I/O 性能损耗；且 Android 限制 `/proc` 部分文件，容器内 `top`/`uptime` 是假数据。→ **可以当"轻量应用服务器"，不能当"Docker 服务器"。【已核实】**
   - 来源：[Termux Wiki: PRoot](https://wiki.termux.com/wiki/PRoot)、[proot-distro README](https://github.com/termux/proot-distro)
4. **Docker/Podman/containerd 在 Android 内核上：本机已实测否决**（USER_NS/PID_NS 未启用，见 §13）。容器需要 user/pid/mount/net namespace、cgroups v2（或可用性）、overlayfs、iptables/nftables（NAT）、seccomp 等；手机厂商内核通常按 Android 需求裁剪这些配置（尤其 `CONFIG_USER_NS`），且 GKI 时代 `systemd` 依赖的 cgroup 委派也不完整。**【已实测否决】**（命令清单见 §5.2）
   - 来源（内核特性侧）：[cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)、[namespaces](https://docs.kernel.org/admin-guide/namespaces/index.html)、[binfmt_misc](https://docs.kernel.org/admin-guide/binfmt-misc.html)、[overlayfs](https://docs.kernel.org/filesystems/overlayfs.html)、[netfilter](https://netfilter.org/)、[seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)
5. **服务化：不 root 用 Termux:Boot + termux-services（runit）**；root 后 systemd 在 chroot 中**不保证可用**（依赖 cgroup/`/proc`/`/sys` 与 PID1 语义），更稳的是 **s6 / runit / supervisord**；Magisk 提供 `service.sh` 开机脚本。**【已核实（工具存在性）】/【待验证（systemd 实际行为）】**
   - 来源：[Termux:Boot](https://wiki.termux.com/wiki/Termux:Boot)、[Termux-services](https://wiki.termux.com/wiki/Termux-services)、[proot-distro README（"No background services"）](https://github.com/termux/proot-distro)
6. **Root 方案**：本机**实测内核 5.4.274-qgki（GKI 1.x 代，非 GKI 2.0）**。→ **Magisk**（成熟、文档全、patch ramdisk）与 **APatch**（内核 patch，支持 3.18–6.12，需 `CONFIG_KALLSYMS_ALL`）更现实；**KernelSU 官方面向 GKI 设备**，非 GKI 要自行集成/编译内核（属于 C 路线）。**【已核实（官方口径）】/【待验证（本机内核世代）】**
   - 来源：[Magisk 文档](https://topjohnwu.github.io/Magisk/)、[KernelSU: What is KernelSU](https://kernelsu.org/guide/what-is-kernelsu.html)、[APatch README](https://github.com/bmax121/APatch)
7. **解锁代价**：小米官方解锁页流程 = 绑账号/设备 + 进 bootloader + 工具解锁，官方明示解锁后**指纹识别、查找手机等安全相关服务变得不可靠**；近年额外门槛（如 168 小时账号绑定、社区等级等）**官方页面未载**，需以申请当时 Mi Community/解锁工具提示为准。解锁还会**清空数据**、破坏 AVB 验证链、影响 Play Integrity 与 OTA（Magisk 官方 OTA 指南要求先还原原厂镜像）。**【已核实（官方页流程/风险提示）】/【待验证（门槛与 OTA 实测）】**
   - 来源：[小米解锁页](https://www.miui.com/unlock/index.html)、[解锁工具下载](https://www.miui.com/unlock/download.html)、[Magisk OTA 指南](https://topjohnwu.github.io/Magisk/ota.html)、[Play Integrity 概览](https://developer.android.google.cn/google/play/integrity/overview)
8. **长期插电是真问题**：锂电长期满电 + 高温会加速老化甚至鼓包；优先找 HyperOS 的「充电保护/旁路充电」；内核侧可尝试 `charge_control_limit` 之类 sysfs（本机是否有**待验证**）；骁龙 888 高负载会热节流，建议限频、关 boost、加强散热；Android 的 Doze/电池优化会杀 Termux/sshd，必须关电池优化 + `termux-wake-lock`；WiFi 省电/漫游会造成 IP 漂移，服务器场景建议静态 IP，最好用 Tailscale/WireGuard 而非公网端口。**【待验证（本机实测）】/【已核实（工具与文档存在性）】**
9. **推荐结论（2026-11-10 定稿，2026-11-11 校准）**：**A（无 Root 的 Termux + proot）为已落地路线**；B（解锁 + root chroot）因国行官方解锁不可用而**取消**；C（自定义内核/原生移植）**未实施且不推荐**。原 A/B/C 论证见 §8/§10（B 已标取消，仅存档）。

## 3. 原生 Linux 移植可行性：haydn 目前「不可行」

### 3.1 逐项目支持现状（2025→2026）

| 方案 | 定位 | 对 SM8350/haydn 的现状 | 结论 | 依据 |
|---|---|---|---|---|
| postmarketOS（现 Nura） | 最接近"手机跑完整 Linux"的社区发行版，pmbootstrap 安装 | **无 haydn 设备页**（Wiki 检索 0 结果）；SM8350 SoC 平台 `Mainline=yes` 但**平台内核包在 archived 目录**，且逐项组件多为 Untested（Display/GPU/Audio/Wi-Fi/Modem/Thermal 均 Untested，USB Partial）；同生态的 Xiaomi SM8350 机型（Mi 11 / Mi 11 Ultra）**标记 not booting** | **不可行（无 port）** | [SoC 页](https://wiki.nura.eco/wiki/Qualcomm_Snapdragon_888_(SM8350))、[Mi 11 venus](https://wiki.nura.eco/wiki/Xiaomi_Mi_11_(xiaomi-venus))、[Mi 11 Ultra star](https://wiki.nura.eco/wiki/Xiaomi_Mi_11_Ultra_(xiaomi-star)) |
| mainline Linux（Linus 树） | 上游内核 | SM8350 平台有**部分**支持（页面称 partial support，且仍在推进，有 #sm8350-mainlining 社区频道）；但手机级 haydn 设备树是否存在**待验证**（`git.kernel.org` 本次抓取失败） | **平台级可行/设备级不可行** | 同上 SoC 页 |
| Ubuntu Touch（UBports） | Ubuntu+Halium 移动系统 | 官方 **111 台**支持设备中无 K40 Pro；`/device/haydn` 返回 **404** | **不可行** | [设备库](https://devices.ubuntu-touch.io/)、[haydn 404](https://devices.ubuntu-touch.io/device/haydn) |
| Droidian | Debian + libhybris + Halium（跑在 Android 内核上） | 依赖 Halium 设备移植；`droidian-devices` 组织内**无 Xiaomi/haydn/alioth 仓库**（抓取 API 列表逐条核对） | **不可行** | [droidian.org](https://droidian.org/)、[droidian-devices](https://github.com/droidian-devices) |
| Mobian | Debian + mainline，面向移动设备 | 官方支持列表 = PinePhone、Librem 5、OnePlus 6/6T、SHIFT 6MQ 等；无 haydn | **不可行** | [mobian-project.org](https://mobian-project.org/) |
| Android AVF（pKVM）官方 VM | Android 官方虚拟化框架（可跑受保护 VM/Linux） | AVF 文档存在；但"Linux Terminal 式 Debian VM"面向较新 Pixel/新内核，2021 年老机型 + 厂商内核大概率**不启用 pKVM** | **待验证（大概率不可用）** | [AVF 文档](https://source.android.google.cn/docs/core/virtualization) |

### 3.2 结论与推论
- 把 K40 Pro 直接刷成 "postmarketOS/Nura/Ubuntu Touch/Droidian" **不是选不选的问题，而是根本没有可刷的镜像**；要自己移植 = 从零写/改 SM8350 设备树 + 面板/触控/Wi-Fi/电源管理，工作量以**人月起**，且上游对 Xiaomi SM8350 兄弟机型的移植都还停在"not booting"。
- 即使移植成功，对"服务器"目标也不划算：服务器真正依赖的是 **Wi-Fi/有线网络、充电管理、热管理、稳定长跑**，而这些恰是 mainline 手机移植最不成熟的部分。
- **对本项目的含义**：第 6 节起的所有可行路线都必须**保留 Android 作为底层平台**（A/B 路线），或走官方虚拟化（待验证）。C 路线（自定义内核）不是"刷 Linux"，而是"在 Android 上换一个更开放的内核"。

## 4. Android 之上跑 Linux：路线对比

| 路线 | 是否需要 root/解锁 | 核心机制 | 需要的内核能力 | 性能 | 服务化 | 容器 | 主要限制 | 结论 |
|---|---|---|---|---|---|---|---|---|
| **A1. Termux 原生**（只用 Termux 包） | 否 | Android 上跑 aarch64 用户态工具链 | 无特殊（普通进程） | 接近原生（无 ptrace） | Termux:Boot + termux-services(runit) | ❌ | 没有 glibc 完整生态；包受 Termux 仓库限制；后台被杀需保活 | **可行但受限（A 的轻量版）** |
| **A2. Termux + proot-distro**（Ubuntu/Debian/Alpine） | 否 | proot = 用户态 chroot/bind/binfmt（ptrace 重写路径） | **不需要** namespace/cgroup；只需能跑 ptrace（Android 允许） | I/O 密集明显慢（编译/包管理尤甚）；纯计算损失小 | ❌ 官方"generally not possible"（systemd/OpenRC） | ❌ 无 cgroups/namespaces | 假 root（不能 mount/iptables）；`/proc/stat` 等被 Android 替换成固定值（监控失真）；套娃 proot 不支持 | **可行但受限（首选 A）** |
| **B1. root + chroot**（Debian/Ubuntu 全发行版） | **要**（Magisk/APatch） | 真 chroot + bind 挂载 `/proc`/`/sys`/`/dev` | 无 namespace 也能 chroot；但服务管理依赖 cgroup/`/proc` | 接近原生（无 ptrace） | 可用 s6/runit/supervisord；systemd **待验证** | 可用 `chroot` 但不是隔离容器 | 需要内核特性配合；root 检测/OTA/保修/Play Integrity 代价 | **可行但受限（B 核心，中高风险）** |
| **B2. root + Docker/Podman/containerd** | **要** | 容器运行时（namespace+cgroup+overlay+netfilter） | user/pid/mount/net/ipc/uts ns、cgroups（v1/v2）、overlayfs、iptables/nftables NAT、seccomp、binfmt_misc（可选） | 好（若内核齐备） | 容器内可跑 systemd/s6 | ✅ | **手机内核通常缺 USER_NS/overlay/cgroup 委派**；Docker 官方未支持 Android；不保证可用 | **已实测不可行（USER_NS/PID_NS 缺失，见 §13）** |
| **B3. AVF/pKVM 虚拟机** | 视设备（官方功能） | Android 虚拟化框架跑 Linux VM | pKVM/GKI 版本要求、虚拟机支持 | 好（隔离最强） | VM 内任意 init | ✅（VM 内） | 老机型/厂商内核大概率无 pKVM；官方 "Linux Terminal" 非通用功能 | **待验证（大概率不可用）** |
| **C. 自定义内核/第三方 ROM + 容器** | **要**（解锁+刷机） | 自己编译开启 USER_NS/CGROUP/overlay 的内核，或基于 LineageOS | 取决于你编译的 config | 最好 | 取决于内核 | ✅（若你开全特性） | 无公开 haydn 容器内核项目；自编译/刷机风险极高、无维护、OTA 不可用 | **不推荐（仅研究）** |
| **D. 原生 Linux（Nura/UT/Droidian/Mobian）** | 解锁 + 刷机 | 见 §3 | 需要完整设备移植 | — | — | — | **没有 haydn 端口** | **不可行** |

**一句话选型**：**A2 是"能马上用"的上限；B1 是"能力上限 + 可控风险"的最优点；B2 要看你手机内核气不气人；D 没门。**

## 5. 容器路线需要的内核特性 vs Android 现实（核心考察点）

任务要求逐项说明：user/pid/mount/net namespace、cgroups v2、overlayfs、iptables/nftables、binfmt_misc、seccomp，以及"Android 内核通常缺什么"。

### 5.1 对照表

| 内核特性 | 为什么容器要它 | 内核文档 | Android/手机内核常见状况 |
|---|---|---|---|
| **User namespace** | rootless 容器、`unshare`、容器内 uid 映射的基础；Docker rootless/Podman rootless 依赖 | [namespaces](https://docs.kernel.org/admin-guide/namespaces/index.html) | **最常被关闭**（安全收敛），`CONFIG_USER_NS` 是否 `=y` 是本机能否 rootless 容器的关键；**待验证** |
| **PID/Mount/Net/IPC/UTS namespace** | 进程/挂载/网络隔离，`docker run` 必需 | 同上 | Android 自身用 mount namespace 做分区隔离，`CONFIG_NAMESPACES` 往往开；但**子项是否全开**需查 config；**待验证** |
| **cgroups v2（单一层级 + delegation）** | 资源限制、`systemd` 与容器运行时的记账/控制基础；rootless Docker 明确要求 cgroup v2 | [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) | Android 内核多为 cgroup v1 风格（或 v2 但被 Android 自己占用/委派受限）；**是 systemd 与 Docker 的最大变数**；**待验证**（`mount \| grep cgroup`） |
| **overlayfs** | Docker overlay2 分层镜像、容器写层 | [overlayfs](https://docs.kernel.org/filesystems/overlayfs.html) | Android 自身大量使用 overlay 挂 /system、/product、/vendor（**能用**），但"任意 upper/lower"是否允许、内核是否开 `CONFIG_OVERLAY_FS` 需实测；**待验证** |
| **iptables / nftables（含 NAT）** | 容器端口映射、出网 NAT、网络隔离 | [netfilter](https://netfilter.org/) | 手机为 USB/热点 tethering 必须有 netfilter；但 `ip_tables`/`nf_tables`/`iptable_nat`/`br_netfilter` 是否全在（Docker 对 NAT/桥接有硬要求）需实测；**待验证** |
| **binfmt_misc** | 跨架构执行（qemu-user）、多架构镜像 | [binfmt_misc](https://docs.kernel.org/admin-guide/binfmt-misc.html) | 常被裁剪；不过 proot 自带模拟，**不依赖内核**；docker 多架构可绕过（用对应架构镜像）；**待验证** |
| **seccomp（+ filter）** | 容器默认 seccomp 策略、减少攻击面 | [seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html) | Android 大量使用 seccomp（app 进程有 seccomp policy），**大概率开启**；但 runc 的默认 profile 是否兼容需实测；**待验证** |
| **其他**：cgroup v2 BPF、`/proc` 完整性、kallsyms、模块加载 | 运行时/监控/调优 | — | Android 限制 `/proc` 部分文件（proot-distro README 已核实 `/proc/stat` 等被替换）；kallsyms 受限影响 APatch 等 |

**为什么"Android 内核通常缺"**（机制层面，非绝对）：
1. Android 的进程模型（每个 App 一个 UID + SELinux + seccomp）**不需要 user namespace**，所以厂商/GKI 常直接不编 `CONFIG_USER_NS`；
2. Android 用 cgroup **v1 的特定控制器**给 App 分组，v2 单一层级并非必需 → 内核可能只按 Android 需求裁剪；
3. Android 完全不需要 "Docker 式 NAT/桥接"，tethering 只需一套简化网络路径 → 某些 netfilter 模块可能缺失；
4. GKI 化后内核配置由 Google 统一，**厂商可加不可减**碰不到的部分（但老机型 5.4 厂商树自由度更大，也更"缺"）；
5. 手机内核没有"给用户跑 systemd 容器"的诉求，**cgroup delegation、/proc 完整视图**这类"服务器日常"不是设计目标。
> 以上为机制推理；**具体缺失项必须以 §5.2 命令在真机上验证后才可写死**（本报告不把推理当结论）。

### 5.2 上机核查命令（拿到 ADB 后直接跑，把输出存档到 `inventory/`，不入库）

```bash
# 1) 内核与机型
adb shell getprop ro.product.device; adb shell getprop ro.board.platform; adb shell uname -a

# 2) 配置项（GKI 设备可能没有 config.gz；没有就用 3) 的替代证据）
adb shell 'zcat /proc/config.gz 2>/dev/null | grep -E "CONFIG_(USER_NS|NAMESPACES|PID_NS|NET_NS|IPC_NS|UTS_NS|CGROUPS|CGROUP_BPF|OVERLAY_FS|BINFMT_MISC|SECCOMP|SECCOMP_FILTER|NF_NAT|IP_NF_NAT|BRIDGE|VETH|KALLSYMS)"'

# 3) 运行时证据
adb shell 'mount | grep -E "cgroup|overlay|binfmt"'
adb shell 'ls -l /sys/fs/cgroup/ 2>/dev/null | head'
adb shell 'cat /proc/filesystems | grep -E "overlay|cgroup|binfmt"'
adb shell 'ls /sys/class/power_supply/'

# 4) 调优节点
adb shell 'ls /sys/devices/system/cpu/cpufreq/; cat /sys/devices/system/cpu/cpufreq/policy0/scaling_available_governors; cat /sys/devices/system/cpu/cpufreq/policy0/scaling_governor'
adb shell 'ls /sys/block/; for b in /sys/block/sd*; do echo $b; cat $b/queue/scheduler; done'
adb shell 'cat /proc/swaps; ls /sys/block/zram0/'
adb shell 'ls /sys/class/thermal/ | head -20'

# 5) 电池/充电控制节点（决定能否做"80% 限充/旁路充电"）
adb shell 'ls /sys/class/power_supply/battery/ | grep -Ei "charge|current|input|bypass|limit"'
adb shell 'cat /sys/class/power_supply/battery/charge_control_limit 2>/dev/null; cat /sys/class/power_supply/battery/charge_control_limit_max 2>/dev/null'

# 6) 温控/降频现状
adb shell 'dumpsys thermalservice | head -60'
adb shell 'cat /sys/class/thermal/thermal_zone*/temp 2>/dev/null | head'
```

**判定门槛（建议）**：以上 2) 中 `USER_NS + CGROUPS + OVERLAY_FS + NET_NS` 全 `=y` 且 3) 能看到 cgroup2 挂载/overlay 可用 → B2（Docker）才有现实可能；否则 B 路线止步于 B1（chroot + s6/supervisord）。

### 6.1 推荐的服务架构（按路线；2026-11-10 设计稿）

> 说明：本节是 A 路线早期设计稿。现行实现已固化为 `scripts/server/00-server.sh` → `ubuntu.sh` → `server-up` + `server-watch`（见 [17 重建手册](../20-server/17-研究平台环境构建手册.md)），并演进为 A+（见 [06 A+优化方案](../20-server/06-A+优化方案.md)）；早期 proot-distro 方案最终改为离线 proot + `ubuntu-base` rootfs。

- **A 路线（无 root）**：
  ```
  Android 开机
    └─ Termux:Boot (~/.termux/boot/start.sh)
        ├─ termux-wake-lock               # 防休眠
        ├─ sshd (openssh, 8022)           # 或由 termux-services 管理
        └─ proot-distro login ubuntu -- <启动脚本>
             └─ supervisord（容器内守护 nginx / 应用进程）
  ```
  - 关键：**服务清单不要超过 3–5 个**；每个服务都按"挂了能自愈"设计（proot 内用 supervisord `autorestart=true`，外层用 Termux:Boot 脚本里的 `while true` 兜底）。
- **B 路线（root chroot）**：
  ```
  Magisk/APatch 开机
    └─ service.sh 或 Termux:Boot
        ├─ mount --bind /proc /sys /dev + 存储目录
        ├─ chroot /data/linux /usr/bin/s6-svscan /run/service   # 或 supervisord
        ├─ chroot 内 sshd(22)、nginx、应用服务
        └─ 可选：Docker daemon（仅当 §5.2 门槛通过）
  ```
- **自启兜底**：无论 A/B，都建议"双保险"——系统层自启（Termux:Boot / Magisk service.sh）+ 应用层自愈（runit/supervisord/systemd 的 restart 策略）。
- **心跳/监控**：A 路线不要指望 `top/uptime`（proot 下被 Android 固定值污染，**已核实**）；用宿主 `adb`/外部 Prometheus node_exporter 或 Tailscale 侧探测；B 路线 chroot 后 `/proc` 真实，可正常用。

## 7. Root 与解锁的现实代价

> **2026-11-11 说明**：B 路线已取消（国行官方解锁不可用，Gate B0 失败），本节保留作**未来换机/研究参考**，不在本机执行。

### 7.1 三套 root 方案对比

| 维度 | **Magisk** | **KernelSU** | **APatch** |
|---|---|---|---|
| 原理 | patch boot/init_boot ramdisk，systemless 模块，Zygisk | **内核态** root，直接在 kernel 里授权用户态进程；模块交由 metamodule（如 meta-overlayfs） | 内核 patch（KernelPatch）/KPM 内联 hook；APM 模块体系 |
| 官方支持面 | 面最广（含老内核/A-B/init_boot） | **官方面向 Android GKI 设备**；非 GKI 需自行集成/编译内核 | **ARM64、内核 3.18–6.12**；需 `CONFIG_KALLSYMS=y` + `CONFIG_KALLSYMS_ALL=y` |
| 对 haydn（2021/SM8350/大概率 5.4 非 GKI）的适配性 | **最稳**（不挑 GKI，靠 ramdisk） | 需确认是否 GKI；否则要编译内核（→ C 路线） | **较好**（覆盖 5.4），前提 KALLSYMS_ALL 开启；否则仅"initial support" |
| 开机自启/模块 | `service.sh`、模块生态最丰富 | metamodule 体系 | APM（类 Magisk 模块）+ KPM |
| 隐藏/检测 | Zygisk + DenyList（**不保证长期有效**） | 内核态相对难检测，但 Play Integrity 仍看设备状态 | 同左；另有 **SuperKey**（权限高于 root，必须妥善保管） |
| 选型结论 | **首选** | 仅在确认 GKI 或愿意编译内核时 | **次选**（若内核 KALLSYMS_ALL 且不想动 ramdisk） |
| 依据 | [Magisk 文档](https://topjohnwu.github.io/Magisk/) | [KernelSU 文档](https://kernelsu.org/guide/what-is-kernelsu.html) | [APatch README](https://github.com/bmax121/APatch) |

### 7.2 解锁的代价清单（做 B 路线前必须签字画押）

| 代价 | 说明 | 状态 |
|---|---|---|
| **数据清空** | 解锁 bootloader 必清用户数据（不可恢复，先备份） | 常识/官方流程隐含 |
| **安全功能降级** | 官方解锁页明确：解锁后"指纹识别、查找手机等对系统安全性依赖性高的功能或服务将变得不可靠" | **已核实**（[官方页](https://www.miui.com/unlock/index.html)） |

| **Play Integrity** | 解锁+root 后部分 banking/支付/游戏/风控 App 可能不可用；DenyList/模块只是缓解，不保证长期 | **已核实（API 存在）**/待验证体验（[Play Integrity](https://developer.android.google.cn/google/play/integrity/overview)） |

| **解锁门槛** | 小米官方页只写"绑账号/设备 + 解锁工具"；近年社区提到 168 小时绑定、社区等级、年度次数等限制 | **已确认不可用**：国行官方解锁入口已关闭（用户 2026-11-10 确认小米社区 App 无入口）；本机不执行解锁 |
| **变砖风险** | 刷错 boot/recovery 需救砖（fastboot/EDL）；老机型社区救砖资源相对多但仍非零风险 | 待验证（需备救砖包） |

| 前置条件 | ① 接受解锁代价（清数据、AVB 破坏、Play Integrity 风险、OTA 变手动、保修风险）；② 解锁资格满足（门槛**以申请时社区公告为准**）；③ 完成 §5.2 内核核查；④ 有救砖包/EDL 资源 |
| 步骤（概要） | 1) 备份 → 解锁（官方流程 + Mi Unlock）→ 2) 装 Magisk（patch boot）或 APatch（查 KALLSYMS）→ 3) 关闭 dm-verity 相关校验（按方案指引）→ 4) 在 `/data/linux` 用 `debootstrap` 装 Debian/Ubuntu（或 LineageOS 下 chroot 发行版包）→ 5) 写自启脚本挂 `/proc`/`/sys`/`/dev` 后 chroot 进 s6 → 6) chroot 内 sshd(22)、nginx、应用；7) **仅当 §5.2 门槛全部通过**再尝试 Docker（先 `hello-world`，再 `nginx`，再 `postgres`） |
| 预期收益 | 真 Linux（glibc 全生态）、无 ptrace 损耗、可绑 80/443/22、可跑数据库/Nextcloud 级应用、容器（若内核允许）、可做 iptables/NAT 与更细的资源控制 |
| 主要风险 | 变砖/救砖；root 检测；Play Integrity/银行 App 不可用；内核缺 USER_NS/CGROUP → Docker 无法跑（B 退化为 B1）；OTA 需手动；电池/散热要求更高 |

| 验收 | chroot 内 `ss -lntp` 正常、连续 30 天 ssh 可达、断电重启自启、`docker run hello-world` 成功（若启用） |

## 13. 上机实测结论（2026-11-10 复核补充）

> 本节由 Lead 在 ADB 直连后补充，**只读探测、未修改设备任何配置**。
> 证据文件：`inventory/capability-probe-latest.txt`（探测原始输出）、`inventory/device-info-latest.json`（设备档案）；
> 探测脚本：`scripts/adb/probe-device.sh` + `scripts/adb/probe-device.ps1`（可重复执行）。

### 13.1 实测事实

| 检查项 | 实测结果 | 结论 |
|---|---|---|
| 代号 / SoC | `ro.product.device = haydn`、`ro.board.platform = lahaina`、`ro.soc.model = SM8350` | §2 结论直接适用，**无 alioth 混淆风险** |
| 内核版本 | `Linux 5.4.274-qgki-gcc3ec22f5061` | **5.4 QGKI（GKI 1.x 代），非 GKI 2.0** |
| 固件 | Android 14 / SDK 34 / HyperOS OS1.0 / `V816.0.15.0.UKKCNXM` | 与 03 手册的刷机基线一致 |
| 启动链 | `ro.boot.flash.locked=1`、`verifiedbootstate=green`、`vbmeta.device_state=locked`、`veritymode=enforcing`、SELinux Enforcing | 未解锁、AVB 完整（与 §7.2 一致） |
| **命名空间** | `CONFIG_NAMESPACES=y`、`UTS_NS=y`、`NET_NS=y`；**`# CONFIG_USER_NS is not set`**、**`# CONFIG_PID_NS is not set`**；`/proc/self/ns` 仅有 `cgroup/mnt/net/uts` | **容器路线否决**：Docker/Podman/containerd 无法创建 pid/user 命名空间；root 也无法绕过，除非自编译内核 |
| 容器相关内核项 | `CONFIG_CGROUPS=y`、`CGROUP_BPF=y`、`# CONFIG_CGROUP_DEVICE is not set`；`OVERLAY_FS=y`、`BINFMT_MISC=y`、`SECCOMP=y`、`SECCOMP_FILTER=y`；`NF_NAT=y`、`NF_NAT_MASQUERADE=y`、`IP_NF_NAT=y`、`IP_NF_FILTER=y`、`BRIDGE=y`、`VETH=y`、`# CONFIG_BRIDGE_NETFILTER is not set` | 单看 cgroup/overlay/netfilter 部分满足，但命名空间是硬门槛 → 仍不可用 |
| cgroup 形态 | **混合模式**：v1 控制器挂 `/dev/blkio`、`/dev/cpuctl`、`/dev/cpuset`、`/dev/memcg`；v2 挂 `/sys/fs/cgroup` 且 `cgroup.controllers` 为空（无委派） | **systemd 在 chroot 里不保证可用**（维持 §6 判断，优先 s6/runit/supervisord） |
| 运行时命名空间测试 | `unshare -U` → `Invalid argument`（对应 USER_NS 缺失）；`unshare -m/-n/-p` → `Operation not permitted`（shell 权限/SELinux 限制） | 与内核配置一致 |
| 分区形态 | **A/B 双分区**：`boot_a/boot_b`、`vendor_boot_a/b`、`dtbo_a/b`、`vbmeta_a/b`、`vbmeta_system_a/b`；另有 `super`（动态分区）、`metadata`、`userdata`、`misc`、`persist`、`logdump` 等；**无 `init_boot`** | 刷机必须按 slot 操作；Magisk 修补 `boot.img`（本机无 init_boot） |
| 充电 / 电池控制 | `/sys/class/power_supply/battery` 对 shell **`Permission denied`**（`charge_control_limit`、`charge_full`、`cycle_count`、`temp` 均不可读）；`/proc/swaps`、UFS `scheduler` 也不可读 | 限充/旁路**必须 Root 后再验证**；当前只能用 HyperOS 系统「充电保护」 |
| 温控 | `dumpsys thermalservice`：ThermalHAL 2.0 已连接、Thermal Status 0（正常）；cooling devices 含 `thermal-cpufreq-4`、`thermal-cpufreq-7`、`cpu-isolate*`、`cdsp` 等 | 温控链路正常，可长期观察 |
| 电源当前状态 | 电池 100% FULL、27 °C、GOOD、AC 供电；屏幕 `Dozing`（息屏休眠） | 空载基线正常 |

### 13.2 对原结论的修正（相对 §1 / §4 / §11）

1. **B2（Docker/Podman/containerd）状态升级：从【待验证/多半不可用】→【已实测否决】**。依据：`USER_NS`、`PID_NS` 在编译期未启用，root 也无法绕过，唯有自编译内核（C 路线）可解。
2. **A 路线（Termux + proot）继续成立**：proot 是用户态 ptrace 实现，不依赖 namespace；本机 `BINFMT_MISC=y`、overlay 可用，不影响 A。
3. **B1（root + chroot）成立但注意 A/B 分区**：解锁后 Magisk 修补 `boot.img` 并按当前 slot 刷入（`boot_a` 或 `boot_b`），必须先备份原厂 boot；本机 `CONFIG_KALLSYMS_ALL=y`，APatch 作为次选可行。
4. **systemd 维持"不保证"**：cgroup v2 无委派 + 混合 v1 → 继续推荐 **s6 / runit / supervisord**。
5. **充电上限仍需 Root**：shell 无权读 battery sysfs，现有条件下只能开启 HyperOS「智能充电保护」；Root 后再试 `charge_control_limit`（若节点存在）。
6. **KernelSU 维持不推荐**：5.4 QGKI（GKI 1.x）需自编译内核 → 首选仍为 **Magisk**。
7. **B 路线最终判定：不可行（2026-11-10 用户确认）**：小米社区 App 无解锁入口，与 2026 年国行官方解锁关闭的政策情报一致；本项目已转 A+ 无 Root 优化（见 [06-A+优化方案](../20-server/06-A+优化方案.md)）。
