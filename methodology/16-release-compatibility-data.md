# MTH-016 · 发布就绪、兼容与数据治理

> **一句话**：把"本地命令跑通"变成**可重复部署、可观测、可回滚、可弃用、可追溯**的交付——本文承接 [MTH-013](12-delivery-governance.md) 的 G5–G6 门（发布就绪与发布观察），给出长期可维护所需的检查项。
> **权威边界**：风险分级、角色/DRI、需求基线卡、阶段门 G0–G7 与用户验收在 [MTH-013](12-delivery-governance.md)；验收证据类型与恢复演练在 [MTH-008](07-validation.md)；不可协商红线在 [guardrails/](../guardrails/README.md)。本文不改动任何门禁与红线，只回答"过 G5/G6 与发布后维护要看什么"。

## 1. 适用场景

- **发布/割接前**：判断"本地构建/命令通过"是否足以对外可见（§2）。
- **接口/字段/版本变化前**：确认兼容承诺、弃用窗口与渐进路径（§3）。
- **采集/保留/外发数据前**：确认最小化、边界与删除验证（§4）。
- **新增依赖/引入第三方制品前**：确认许可、来源与可追溯性（§5）。
- **丢失症状**：只在本地验证就宣布可用；旧 APK 连新服务端的组合无人声明；弃用没有替代与窗口；数据留在 `inventory/` 无限期；依赖许可在发布当天才发现冲突。

## 2. 发布与割接就绪（G5）

"本地构建/命令通过"≠"可发布"。生产/外部可见的 M/H 变更发布前至少完成：

### 2.1 可重复部署

- 记录目标环境（Android 大版本/ABI、Termux/rootfs 版本、依赖服务）与支持矩阵；配置项有说明、默认值与安全存储方式（凭据不写文档，[GRD-006](../guardrails/GRD-006-secret-hygiene.md)）。
- 部署步骤由**非作者**按文档在干净环境或等价 staging 演练，记录命令、版本、结果与人工步骤；有健康检查/启动检查与最小 smoke test；明确哪些环境无法自动验证。
- 数据迁移/回滚/恢复按 [MTH-008](07-validation.md) §6 演练并记录；向前/向后兼容按本文 §3 验证。

### 2.2 可观测与可诊断

- 说明关键流程健康信号（SLI）与阈值（SLO 或等价目标）；无法承诺精确 SLO 时先定义检测信号与人工巡检节奏。
- 明确关键错误、依赖不可用、队列积压、任务失败如何被发现；告警可行动、谁接、何时升级。
- **日志/指标/追踪字段名属于消费者契约**：改名/删除/改语义遵循 §3；禁止遥测含凭据/个人敏感数据（[GRD-006](../guardrails/GRD-006-secret-hygiene.md)、[GRD-011](../guardrails/GRD-011-privacy-inventory.md)）。

### 2.3 runbook 与事件响应

- 生产服务必须有短而可操作的 runbook：检测信号 → 初步判定 → 止损 → 回滚/恢复 → 升级联系人 → 复盘记录位置；指定主责与替补；无持续值班能力时写明支持时段与响应预期，不能假装 24×7。
- 事故处理：先保护人/数据/服务并控制影响；记录时间线、影响范围、已采取动作与不确定项；禁止为"修得快"销毁证据；恢复后复核数据完整性并用可复用教训沉淀 PIT。

### 2.4 Go / No-Go 发布卡

| 字段 | 内容 |
|---|---|
| DRI / 发布 Owner / 时间窗口 / 目标环境 | 谁签、谁盯、何时、在哪 |
| 版本、源提交、制品/固件校验值 | 可追溯（对齐 §5 与 [GRD-014](../guardrails/GRD-014-firmware-freeze-ota.md)） |
| 需求基线与已知不做项 | 链接 REQ/需求卡 |
| 构建/测试/安全/许可/迁移结果 | 命令+退出码+证据位置；未执行项列明 |
| 部署与 smoke test 结果 | 非作者复现 |
| 监控、告警阈值、观察窗口、响应人 | 见 §2.2 |
| 回滚触发条件、步骤、恢复验证 | 见 [GRD-004](../guardrails/GRD-004-backup-before-change.md) |
| 未解决风险及批准豁免 | 批准人 + 到期日 |
| 决策：GO / NO-GO / 有条件 GO | 签核人 + 日期 |

> 模板见 [runbook 模板](../toolkit/templates/runbook.md)；本仓库尚未有真实 Go/No-Go 签核记录（待落地）。

## 3. 兼容、升级与弃用

### 3.1 兼容对象清单（本仓库特有）

| 生产者 | 消费者 | 兼容承诺 |
|---|---|---|
| Android 宿主大版本 / OEM ROM | Termux、Bridge APK、Termux:Boot | 升级前核对 FGS 类型、自启/省电策略（profile 记录） |
| Bridge APK 版本 | 服务端合并/降级逻辑、控制面 | 旧 APK 连新服务端、新 APK 连旧服务端都要声明支持矩阵 |
| profile schema / 遥测字段名与语义 | assess/plan、控制面、仪表盘、审计与告警 | 字段即契约：新增须可选；改名/删除走 §3.2 |
| rootfs/依赖版本 | 服务器栈与备份脚本 | 仅支持同步升级时必须声明停机与迁移要求 |
| 固件/OTA 版本 | 解锁/Root 前提、救援包 | 冻结与受控升级见 [GRD-014](../guardrails/GRD-014-firmware-freeze-ota.md) |

矩阵写法：`生产者版本 | 消费者版本 | 支持？ | 升级先后/限制 | 测试证据`；**没有测试证据的"支持"按不支持**。

### 3.2 破坏性变更的渐进路径

- **必须**：先新增兼容入口/字段/格式（可双读/双写），迁移消费者后切默认，公告弃用窗口后才移除旧入口；数据迁移用 **expand → migrate/backfill → switch → contract**，删除旧 schema 前验证所有活跃消费者已迁移。
- **必须**：弃用条目写清替代方案、开始版本/日期、最早移除版本/日期、影响对象、迁移步骤、检查方式与负责人；只有替代项稳定可用后才启动弃用；安全/数据丢失风险可缩短周期但须说明理由与回退风险。
- **禁止**：把"只支持同步升级"藏起来不写；没有版本兼容承诺的系统必须显式声明停机/迁移要求。

### 3.3 生命周期状态

- 本仓库统一：`draft（Experimental/开发中）→ current（Stable）→ deprecated（Deprecated）→ archived（Removed）`；对外契约（profile schema、遥测字段、CLI 输出 schema）必须声明所处状态。
- 稳定契约需兼容承诺；deprecated 必须给出窗口与替代；archived/移除必须版本升级、迁移指南与变更记录（见 [MTH-011](10-document-lifecycle.md) §2.4 ADR 纪律）。

## 4. 数据治理与隐私

隐私治理处理**个人数据与敏感业务数据的全生命周期**，不只是防 token 泄漏；对齐 [GRD-011](../guardrails/GRD-011-privacy-inventory.md)。

### 4.1 本仓库数据地图

| 数据 | 位置/形态 | 最小化要求 | 保留与删除 |
|---|---|---|---|
| 设备档案（型号/版本/网络能力/序列号风险） | `profiles/`（gitignored） | 脱敏后仅放 `cases/`；序列号不入库 | 换机/任务完成后按用户要求删除 |
| 采集快照/会话产物 | `inventory/`、临时目录（gitignored） | 只存任务必要字段 | 默认短期保留（建议 ≤30 天）后清理 |
| 备份/密钥材料 | `backup/`、`.env`（gitignored） | 加密存储、最小权限 | 按 RPO/保留策略；删除须验证含缓存/日志 |
| soak/验收证据 | 验收报告/JSON（脱敏） | 地址/端口/凭据/个人数据一律脱敏 | 随验收归档；不保留可识别个人数据 |
| 桥遥测（宿主状态） | 本机 HTTPS、日志/快照 | 只读、最小字段、loopback | 按控制面保留策略；禁止外发 |

### 4.2 必须回答的六问

| 维度 | 必须回答 |
|---|---|
| 数据与来源 | 收集/生成哪些数据？来自哪里？是否含真实用户/生产数据？ |
| 目的与依据 | 为何需要？用于什么？授权/同意由项目责任人核实（本文不是法律意见） |
| 最小化与访问 | 能否少收/脱敏/聚合？谁读写/导出？如何审计？ |
| 共享与处理者 | 是否发送给 Agent 服务、模型供应方、分析平台或第三方？数据是否离开受控边界？ |
| 保留与删除 | 保留期限/触发条件？如何验证删除（含缓存/日志/备份）？ |
| 事件处置 | 误发/越权/泄漏如何检测、止损、通知 Owner/隐私负责人？ |

- **禁止**：把生产数据或个人信息输入未获批准的模型、网页、工单、测试 fixture 或协作渠道；数据是否可外发由用户/数据负责人依适用政策裁定。
- **必须**：验收/研究记录只保存必要、脱敏、限权内容；研究数据默认不保留可识别个人身份信息。
- **必须**：删除请求与保留义务冲突、跨境/监管义务、同意依据等法律问题升级给有权限的人处理。
- **未实测声明**：本仓库尚未演练"删除后验证（含备份）"流程，标待落地；不以"符合隐私框架"自证合规。

## 5. 依赖、许可与制品来源

对齐 [GRD-010](../guardrails/GRD-010-license-compliance.md) 与 [GRD-014](../guardrails/GRD-014-firmware-freeze-ota.md)。

- **零依赖优先**：`toolkit/` 必须保持零第三方运行时依赖（当前已满足，见 [toolkit/README.md](../toolkit/README.md)）；新增依赖须评估许可、体积、可复现与安全影响（M 级流程）。
- **Android Bridge 依赖**：记录 SDK/库版本、许可证与更新策略；构建输入可追踪（版本/哈希），自动更新须配合测试与评审，不能只锁不更新。
- **固件与工具来源**：解锁/Root/救援涉及的固件包与刷机工具必须记录来源、版本与 SHA-256 校验（见 [PIT-024](../pitfalls/PIT-024-flash-tool-supply-chain.md)）；来源无法确认的二进制不得宣称为本项目官方推荐制品。
- **许可证**：登记直接依赖与分发许可；出现限制/冲突时暂停分发并由负责人审查；机器可读 SPDX 表达不能替代法务审查。
- **漏洞**：扫描依赖与构建镜像；阻断阈值按可利用性/暴露面/数据影响定义，例外必须写 Owner/理由/期限，不得永久无理由豁免。
- **制品来源（SBOM/provenance）渐进**：阶段一"记录源提交+构建步骤+制品哈希"→阶段二生成 SBOM（SPDX/CycloneDX）→阶段三构建 provenance/签名/消费者验证。**本仓库目前只做到阶段一的文本记录，SBOM 与 provenance 未落地**（标待落地，SBOM 术语见 [MTH-010](09-glossary.md)）。
- **例外**：不能生成 SBOM/扫描/签名时，说明技术原因、替代控制、风险 Owner 与复查日期；不得虚报"扫描通过"。

## 6. 反例

| 反例 | 为什么错 | 正确做法 |
|---|---|---|
| 无回滚演练 | 失败时无法恢复，[GRD-004](../guardrails/GRD-004-backup-before-change.md) 违规 | 恢复未演练视同无回滚 |
| 遥测/日志输出凭据或个人信息 | 越权暴露、违规且不可撤回 | 脱敏 + 最小化 + 访问控制 |
| 只说"支持旧版本"却无证据 | 兼容事故在发布后才暴露 | 矩阵 + 测试证据，否则声明不支持 |

> 交付流程层面的反例与交付前总自检见 [MTH-013](12-delivery-governance.md) §9。
