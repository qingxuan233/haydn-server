# MTH-003 · 通用路线图（P0–P6）

> **结论先行**：改造必须**分阶段推进**，共 7 个阶段（P0–P6），每阶段有明确**交付物、门禁、估时、回滚**。
> 默认只用 **A/A+（无 Root）** 路线；**P4 是"是否升级能力上限"的决策门**，不是必做阶段——多数场景在 P4 直接判定"维持 A+"并跳过 B/C/D。
> **一次只推进一个变更**；门禁未过→回退到上一个稳定状态并记录 blocker；**任何阶段都允许停在原地长期运行**。

---

## 1. 阶段总览

| 阶段 | 目标 | 核心交付物 | 转出门禁 | 熟练估时 | 失败退回 |
|---|---|---|---|---|---|
| **P0 评估与建档** | 用探测数据决定路线，而不是凭感觉 | 设备档案 `profile.json` + 评估结论 + 风险/未知项清单 | **G-A** | 1–2 h | 无破坏性操作，重测即可 |
| **P1 宿主准备** | 让手机具备"可无人值守启动的 Linux 宿主" | Termux/Boot 基线、保活与自启脚本骨架、重启实测记录 | **G-HOST** | 2–3 h | 停止脚本、卸载 Termux 伴生 App |
| **P2 服务器基座** | 可远程登录、服务可自愈的最小服务器 | proot 环境、服务守护、核心服务、局域网入口、备份脚本 | **G-CORE** | 3–6 h | 删除启动脚本、停服务、恢复配置快照 |
| **P3 遥测桥与集成**（可选） | 补齐宿主状态；建立"来源+新鲜度"数据契约 | 桥（只读本机 HTTPS）、服务器侧合并、来源/降级标记 | **G-BRIDGE** | 1–2 天 | 停用桥并回退 Termux 采集；卸载 App |
| **P4 能力上限评估**（决策门） | 判断是否值得 B/C/D 升级 | 升级决策记录（含代价/风险/门禁结论） | **G-B0 / G-B** | 1–2 h（不含等待解锁资格） | 维持 A+，不执行任何破坏性操作 |
| **P5 优化与加固** | 降低温度/功耗、补安全与运维韧性 | A+ 优化清单、加固项、安全基线 | **G-OPT** | 0.5–2 天 | 每项独立回滚（设置/包/配置可逆） |
| **P6 稳定运行与交接** | 从"能跑"到"可维护、可交接" | soak/重启/恢复演练证据、runbook、Agent 交接包 | **G-SOAK / G-REL** | 持续（≥7 天观察） | 冻结变更、回滚最近一次改动 |

> **门禁定义**：G-A=评估完整且路线结论可复核；G-HOST=重启后宿主自启链路可复现；G-CORE=核心服务与局域网入口通过验收；G-BRIDGE=桥自启/只读/回退通过验收；G-B0=官方解锁可行性与代价可接受（不可行则 B 路线终止）；G-B=A 路线稳定 ≥7 天后判定"是否升级"；G-OPT=优化项逐项验证且可回滚；G-SOAK/G-REL=持续观察与恢复演练达标。

## 2. 各阶段详情

### P0 · 评估与建档

| 项 | 内容 |
|---|---|
| 目标 | 拿到结构化设备档案与路线结论，明确"能做什么/不能做什么/待验证什么" |
| 前置 | 设备可用；PC 侧有 ADB 工具；设备所有者同意只读探测 |
| 关键动作 | `detect` 采身份 → `probe` 采能力（内核/命名空间/cgroup/存储/加密/权限）→ `assess` 出路线与门禁 → **人工复核**每条结论的来源（实测/文档/假设） |
| 交付物 | 脱敏 `profile.json`（运行期存 `profiles/`，不入库）；评估输出（route/confidence/gates/blocked/next_steps）；风险与未知项清单 |
| 门禁 G-A | 档案字段完整度满足决策；路线与约束自洽；`unknowns` 有明确验证计划；**未通过不得开始改造** |
| 回滚 | 纯只读，无回滚需求；重跑探测即可 |
| 不要做 | 不要在评估阶段顺手改系统设置；不要把"待验证"写成已通过 |

### P1 · 宿主准备

| 项 | 内容 |
|---|---|
| 目标 | Android 宿主具备启动 Linux 用户态、断电恢复、后台保活的基线能力 |
| 前置 | P0 门禁通过；路线为 A/A+（B/C/D 须走 P4 决策） |
| 关键动作 | 开 USB 调试并完成首次授权 → 装 Termux + Termux:Boot → 电池优化白名单/后台运行豁免 → 解锁策略（无锁屏凭据或接受人工启动）→ wake-lock 与自启脚本骨架 → **重启 1 次验证链路** → 维护完成后关闭 ADB |
| 交付物 | 宿主基线记录（权限/白名单/自启方式）；启动脚本骨架；重启自启实测记录 |
| 门禁 G-HOST | 重启后无需 PC/ADB 即可启动 Termux 与自启脚本；保活未被系统清理；失败可在现场人工恢复 |
| 回滚 | 删除 `~/.termux/boot/` 脚本；停用/卸载伴生 App；恢复系统设置原值（先记录原值） |
| 不要做 | 不要批量禁用系统包；不要 `am kill-all`；不要默认启用公网 ADB |

### P2 · 服务器基座

| 项 | 内容 |
|---|---|
| 目标 | 手机成为"可远程登录、核心服务可自愈、数据可备份"的 Linux 小服务器 |
| 前置 | G-HOST 通过；已确认内核不满足容器条件时**不尝试容器**（见 [MTH-004](03-server-stack.md)） |
| 关键动作 | 准备 rootfs（离线/在线均可，慢网络优先离线）→ 装服务守护（supervisord）→ 装核心服务（远程登录 + 反向代理/TLS + 最小状态页）→ 写入自启链 → 日志轮转 → 备份脚本 + 恢复入口 → 局域网访问验收 |
| 交付物 | 服务配置（入配置管理/备份）；局域网入口；备份包与恢复命令；服务清单与资源预算 |
| 门禁 G-CORE | 重启后核心服务自动恢复；局域网入口健康检查通过；备份可恢复（演练一次）；资源占用在预算内 |
| 回滚 | 停服务 + 恢复配置快照；必要时回退 rootfs 备份（见 [MTH-004](03-server-stack.md) 备份章节） |
| 不要做 | 不要在 proot 内装 systemd/容器；不要超过资源预算堆服务；不要把凭据写进配置仓库 |

### P3 · 遥测桥与集成（可选但推荐）

| 项 | 内容 |
|---|---|
| 目标 | 服务器能拿到 App 可访问的宿主状态（电池/网络/屏幕/前台应用等），并带来源与新鲜度 |
| 前置 | G-CORE 通过；Android 14+（`specialUse` FGS 场景）；设备所有者同意安装伴生 App |
| 关键动作 | 构建/安装只读桥 → 系统权限与 OEM 白名单 → 仅 loopback HTTPS + 凭据 + 证书校验 → 服务器合并状态并标注来源 → 定义回退（桥不可用→Termux 采集） |
| 交付物 | 桥 release 构建物与安装记录；合并后的状态 API；来源/新鲜度字段；回退验证记录 |
| 门禁 G-BRIDGE | 重启 N 次桥均自启；非授权请求被拒绝；非 loopback 不可达；停桥后服务器正确回退且不伪造数据 |
| 回滚 | 卸载桥/停用桥；服务器切回 Termux 采集（不影响 A 轨） |
| 不要做 | 不要给桥开写/exec/任意 URL 端点；不要把桥 token 交给控制面或日志；不要把缺失字段补 0 |

### P4 · 能力上限评估（决策门，默认不升级）

| 项 | 内容 |
|---|---|
| 目标 | 用数据回答"是否值得解锁/刷机换能力上限" |
| 前置 | P2（或 P3）稳定运行；设备所有者愿意讨论清数据/保修/完整性代价 |
| 关键动作 | 查 OEM 官方解锁策略与门槛 → 评估 root 方案与内核能力（需容器才评估 NS/cgroup）→ 评估社区移植/自编译条件 → **G-B0** 判定官方解锁是否可行 → 通过后再评估 G-B（A 路线稳定 ≥7 天是否仍需要升级） |
| 交付物 | 升级决策记录（做/不做/换机）；代价清单；如做，B/C 路线执行计划与救砖预案 |
| 门禁 G-B0 / G-B | G-B0：官方解锁可用（`bootloader_unlocked` / `oem_unlock_policy`）+ 用户书面接受清数据/保修/完整性代价；**不可用→B 终止，保持 A+**。G-B：数据证明 A+ 已到瓶颈 |
| 回滚 | 决策门本身无破坏；执行 B/C 后回滚需官方镜像/救砖包（**未备齐不得开始**） |
| 不要做 | 不要用第三方付费/漏洞解锁；不要在未备份/无救砖方案时解锁；不要为"折腾"而升级 |

### P5 · 优化与加固

| 项 | 内容 |
|---|---|
| 目标 | 降低温度/功耗与噪声，提升长期稳定性和安全性 |
| 前置 | P2/P3 验收通过；有可回滚的变更方式（记录原值/快照） |
| 关键动作 | 显示/动画/刷新率类低风险设置 → 充电策略与温控 → 网络可达与发现（**不要求**静态租约/路由器权限；动态地址 + 发现兜底）→ **逐包**治理（只 disable，不 uninstall）→ 日志/磁盘水位 → 安全加固（凭据、权限、暴露面、备份加密、控制面分级） |
| 交付物 | 优化项清单（每项含原值/新值/收益/风险/回滚）；加固项清单；前后指标对比 |
| 门禁 G-OPT | 每项单独验证；核心服务无中断；温度/负载不恶化；安全暴露面通过核对 |
| 回滚 | 每项独立回滚（设置恢复原值、包重新 enable、配置回滚快照） |
| 不要做 | 不要卸载系统包（[GRD-002](../guardrails/GRD-002-no-system-package-uninstall.md)）；不要批量改设置；不要在 soak 窗口内改核心配置 |

### P6 · 稳定运行与交接

| 项 | 内容 |
|---|---|
| 目标 | 从"能跑"到"能维护、可观测、可交接" |
| 前置 | P5 完成；关键链路都有回滚路径 |
| 关键动作 | 起持续观察（≥24h soak，长期目标 7/30 天）→ 重启 N 次复测 → 故障注入（进程退出/断网/凭据失效/超时）→ 恢复演练（备份→恢复→验收）→ 固化 runbook + 门禁证据 → Agent 交接（读序/校验/待办） |
| 交付物 | soak 记录（可用率/失败次数/回退次数）；故障注入与恢复演练记录；runbook；交接清单 |
| 门禁 G-SOAK / G-REL | 目标可用率达标且无崩溃循环；恢复演练通过；异常时降级/回滚被实测 |
| 回滚 | 冻结变更；回退最近一次改动；必要时整体重建（按 runbook） |
| 不要做 | 不要用单次健康检查替代 soak；不要在观察期"顺便优化"；不要删掉失败记录 |

## 3. 阶段状态机与转入/转出

```text
planned ──开始──▶ in_progress ──交付──▶ gate_review
   ▲                    │                    │
   │                    │失败                 ├─通过──▶ done ──(下一阶段)
   │                    ▼                    │
   └────重新规划──── blocked ◀──门禁失败──────┘
                        │
                        └─修复/回滚──▶ in_progress（或回到上一个 done）
```

| 状态 | 含义 | 进入条件 | 离开条件 |
|---|---|---|---|
| `planned` | 未开始 | 上一阶段 `done` 或本阶段被判定为可选 | 领取任务并记录 owner |
| `in_progress` | 实施中 | 前置满足、备份就绪 | 交付物齐备，申请门禁 |
| `gate_review` | 等待验收 | 有可复核证据 | 门禁通过→`done`；失败→`blocked` |
| `done` | 已完成 | 证据入库 | 仅允许因新证据回退（记 ADR） |
| `blocked` | 被阻塞 | 门禁失败或外部条件缺失 | 修复后回 `in_progress`；否则回上一 `done` |
| `rolled_back` | 已回滚 | 变更失败且已执行回滚 | 重新评估后回到 `planned` |

**转入转出规则（必须）**

1. 不允许跳过 P0/P1 直接上 P2；P3 可跳过（代价是宿主状态不可得，需在 DoD 中标注）。
2. 每阶段**只有一个 owner**；多 Agent 并行时写范围必须互斥，同一文件同一时间一个 writer。
3. 每阶段完成必须有**门禁证据**（命令输出/日志/记录），不得用文档叙述替代。
4. 门禁失败连续 2 次 → 停止推进，重新规划（re-plan）并记录原因，而不是反复重试。
5. **Track A 与 Track B/P3 可在 P2 之后并行**，但共享的权限/白名单变更必须串行（一次一个变更）。
6. 阶段可以**长期停留**：一个阶段稳定运行数月再进下一阶段是完全合法的结果。

## 5. 变更管理（必须）

| 规则 | 要求 |
|---|---|
| 一次一个变更 | 一次只改 1–2 个相关项，改完立即验证（重启/健康检查/日志） |
| 先备份 | 变更前有配置快照/数据备份，并记录恢复路径 |
| 可回滚 | 每个变更写明回滚步骤；**回滚未演练 ≙ 没有回滚** |
| 验收证据 | 变更后用可复核证据判定成败；失败先回滚再分析 |
| 记录 | 变更写入 ADR 或变更记录（背景/选项/结论/代价/回滚）；对外契约变化写变更记录 |
| 窗口 | 高风险变更选在可恢复窗口（有人在场/可现场救援） |
| 红线 | 与 [guardrails/README.md](../guardrails/README.md) 冲突的"便捷修复"一律拒绝 |

**变更分类与要求**

| 类别 | 例子 | 备份 | 验收 | 人工在场 |
|---|---|---|---|---|
| 低风险 | 显示/动画设置、日志轮转、只读查询脚本 | 记录原值 | 抽样检查 | 否 |
| 中风险 | 服务配置、权限授予、包 disable、备份策略 | 配置快照 | 全量健康检查 + 重启 1 次 | 建议 |
| 高风险 | 解锁/刷机/root、删除服务、改认证、系统包治理批次 | 完整数据备份 + 救砖预案 | 门禁 + 回滚演练 | **必须** |

**变更记录最小字段**：`id`（ADR/BL）、背景、涉及文件/路径、备份位置、回滚步骤、验收证据、结果、日期。

## 6. 不要做什么（负面清单）

1. ❌ 跳过 P0 评估直接改造；把假设写成实测。
2. ❌ 默认 Root/解锁/刷机（[GRD-001](../guardrails/GRD-001-no-root-no-unlock-default.md)）；第三方解锁一律不做。
3. ❌ 卸载系统包（只允许 disable 且有保护名单）；`am kill-all`（[GRD-002](../guardrails/GRD-002-no-system-package-uninstall.md)、[GRD-003](../guardrails/GRD-003-no-kill-all.md)）。
4. ❌ 在未备份/无回滚方案时改系统设置或服务配置。
5. ❌ 在 soak 观察窗口内改核心配置（破坏证据有效性）。
6. ❌ 引入未授权外部服务或新增公网暴露。
7. ❌ 一次性大批量改包/改配置（无法归因、无法回滚）。
8. ❌ 用"文档声称/代码存在/单次健康检查"替代验收证据（[GRD-013](../guardrails/GRD-013-no-fake-acceptance.md)）。
9. ❌ 为让指标好看而删除失败记录或改写历史结论（案例冻结原则）。
10. ❌ 把目标值（如可用率、资源上限）当成本次实测值写进状态。

## 7. 进度与延期管理

| 现象 | 常见原因 | 对策 |
|---|---|---|
| 门禁反复失败 | 探测不足/假设错误/外部条件未满足 | 回退到 P0 补探测；把假设改成 `unknowns` 并给出验证计划 |
| 重启后不自启 | 锁屏/FBE 延迟、OEM 清理、白名单缺失 | 先查自启链与系统策略，再改脚本；不许用"多试几次"当结论 |
| 服务频繁被清理 | 资源超预算、LMK、后台策略 | 精简服务/降内存/加白名单；见 [MTH-004](03-server-stack.md) |
| 不稳定但说不清原因 | 无观测、无基线 | 先补 soak/指标，再做变更 |
| 时间超预算 | 把等待时间（解锁资格/备件）算进了工作量 | 估算只含"有效投入"；等待单列为外部依赖 |

**门禁未过的三种合法处理**：① 补证据再验；② 降级目标（例如从"7 天稳定"降到"24h 稳定"并标注）；③ 回退到上一 `done` 并停止推进。**不允许**：伪造证据、跳过门禁、把失败改写成"部分完成"。
