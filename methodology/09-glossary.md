# MTH-010 · 术语表（统一口径）

> **用途**：为方法论、工具链、踩坑库与案例提供**唯一术语口径**，避免同一个词在不同文档里含义漂移。
> **规则**：术语首次出现给出中文+英文；正文优先用本表定义；命令、字段名、ID 前缀保持 ASCII 原样。
> **维护**：新增术语必须同时写入本表与出处文档；定义必须**设备无关**（不绑定具体机型/厂商/端口）。

---

## 1. 使用方式（Agent 快速路径）

1. 读文档遇到陌生术语 → 用本表检索（按类别或首字母）。
2. 同一术语在不同上下文含义不同时，以本表 + 出处文档为准，并在 PR/变更记录中说明差异。
3. 发现定义与实现不一致：以 `methodology/` 规范为准，修正工具与文档（见 [MTH-009](08-agent-handoff.md)）。
4. 术语表不收录**环境相关值**（IP、端口、token、序列号、账号），这些一律不入库（[GRD-006](../guardrails/GRD-006-secret-hygiene.md)）。

## 2. 宿主与 Android 机制

| 术语（英文） | 一句话定义 | 为何重要 |
|---|---|---|
| Android 宿主 | 被改造的手机本体；方法论中始终保留 Android 作为底层平台，Linux 跑在它之上。 | 决定了"无 Root 边界"与所有能力的上限。 |
| Bootloader | 引导加载器；解锁状态决定能否刷写/root，生产设备默认**保持锁定**。 | 锁定是默认前提；解锁属于高风险、仅专用实验设备按 [GRD-015](../guardrails/GRD-015-root-lab-controlled.md) 受控的例外。 |
| bootloader_unlocked | 设备档案中的布尔字段：Bootloader 当前是否可写。 | 它是路线决策 A/B 的第一分叉条件。 |
| AVB（Android Verified Boot） | 系统启动链完整性校验，锁定设备通常为 green/校验通过状态。 | 解锁会破坏 AVB，进而影响 OTA/完整性；是路线代价清单的硬项。 |
| dm-verity | 对系统分区做块级完整性校验的机制。 | 锁定+enforcing 是"不刷机可保命"的基础。 |
| FBE（File-Based Encryption） | Android 文件级加密；用户未解锁前部分目录不可读。 | 影响无人值守自启：BOOT_COMPLETED 可能晚于用户解锁，需据此设计自启策略。 |
| FGS（Foreground Service） | 带前台通知、优先级较高的 Android 服务。 | 宿主常驻采集只能靠 FGS 存活，是遥测桥的生存方式。 |
| specialUse | Android 14+ 的前台服务类型，适合"监控/状态桥"这类系统难以归类的用途。 | 桥若不选对 FGS 类型，Android 14+ 直接无法启动。 |
| A/B 分区 | 系统镜像双槽（slot_a/slot_b），刷机/回滚按 slot 处理。 | 影响任何刷写型路线的回滚与救砖方案。 |
| GKI（Generic Kernel Image） | 统一内核镜像代际；决定 root 方案与内核能力可探测性。 | 判断 Magisk/KernelSU/APatch 可行性与容器能力的前提。 |
| OEM | 手机厂商/定制 ROM（如 MIUI/HyperOS/One UI/ColorOS）。 | OEM 差异只允许进入 profile，不得进入核心代码。 |
| OEM profile | 某个厂商/ROM 的适配档案：安装、自启、省电、权限重置等人工步骤。 | 使方法论"设备无关、适配可插拔"，换机不重写核心。 |
| OEM 解锁策略 | 厂商是否开放官方解锁、门槛与代价（清数据/保修/完整性）。 | 是门禁 G-B0 的判定对象；不可用则 B 路线直接终止。 |
| ROM | 设备上运行的系统固件版本。 | 版本差异会改变权限重置与后台策略，需记录在 profile。 |
| Play Integrity | Google 的设备完整性判定，解锁/Root 后常失败。 | 用户若依赖银行/支付类 App，B/C 路线不可选。 |
| 深度测试（Deep Test） | 一加/真我等 OEM 的官方 BL 解锁申请流程（账号/实名/名额/有效期）。 | 决定新机能否走官方解锁；见 [PIT-022](../pitfalls/PIT-022-oem-unlock-quota.md)。 |
| ARB / e-fuse | 硬件级防回滚：安装特定构建时烧断电子熔丝，之后不可软件降级。 | 触发后旧固件/旧 ROM/EDL 可能直接硬砖；见 [PIT-023](../pitfalls/PIT-023-oneplus-arb-hard-brick.md)。 |
| EDL / 9008 | 高通紧急下载模式（9008），用于深刷/救砖；需要匹配 loader/授权。 | 属于救援最后手段，不得用于绕过解锁或再刷旧固件。 |
| OFP / 全量包 | OEM 完整固件包（含 boot 等镜像），用于恢复/重刷。 | 救援与版本一致性核对的基础；必须离线保存并校验哈希。 |
| KMI | 内核模块接口版本（如 `5.10-android12-9`），决定 GKI 内核/模块兼容。 | Root 补丁/内核刷写前必须核对，KMI 不符会 bootloop。 |
| kernel manager / LKM | KernelSU 等的加载方式；LKM 以可加载模块注入，不替换 boot 分区。 | 首选 Root 方式：不触发 AVB、可临时卸载、OTA 友好。 |
| APatch / Superkey | 另一类内核补丁 Root 方案；以超级密钥解锁管理权限。 | KernelSU 不可用时的备选；必须强密码并留存。 |
| systemless / metamodule | 不改系统分区的模块化/挂载方案；KernelSU 改 `/system` 需 metamodule。 | 保持可回滚、避免写死动态分区。 |
| Doze / 电池优化白名单 | Android 的省电休眠机制及其豁免名单。 | 不在白名单的 Termux/桥会被杀，是"重启后掉线"的高频根因。 |

## 3. Linux 运行环境

| 术语（英文） | 一句话定义 | 为何重要 |
|---|---|---|
| Termux | Android 上的终端/包管理环境，提供用户态 aarch64 工具链。 | 无 Root 场景下唯一成熟的 Linux 入口。 |
| Termux:Boot | Termux 的伴生 App，通过系统广播执行 `~/.termux/boot/` 脚本。 | 无 Root 时服务器自启的唯一稳定机制。 |
| proot | 用户态 chroot + bind + ptrace 路径重写实现，不需要真 root。 | A 路线的核心机制；也带来 I/O 损耗与假 root 限制。 |
| proot-distro | Termux 内的发行版管理工具（可装 Ubuntu/Debian/Alpine）。 | 决定 rootfs 从哪来；离线安装是慢网络下的稳健替代。 |
| chroot | 真 root 下的根目录切换；需要 root/解锁路线（B）。 | 与 proot 的能力差异是 A/B 路线分水岭。 |
| Root | 获得系统最高权限的改造；方法论默认禁止，需显式授权与门禁。 | 决定内核调参、特权遥测、真 chroot 能否做。 |
| supervisord | 用户态进程守护器，按配置拉起/重启服务。 | proot 内没有 systemd 时的标准服务管理方案。 |
| systemd | Linux 标准 init/服务管理器，依赖 cgroup、PID1 与 `/proc` 语义。 | proot 内一般不可用；这是"为什么用 supervisord"的根本原因。 |
| USER_NS（用户命名空间） | 内核命名空间之一，rootless 容器的基础。 | 缺失则 Docker/Podman 不可用，容器路线被否决。 |
| PID_NS（PID 命名空间） | 隔离进程 ID 视图的命名空间。 | 与 USER_NS 一起决定容器可行性。 |
| cgroup v1 / v2 | 内核资源分组与限制机制的两个代际；v2 支持委派是 systemd/容器基础。 | 手机内核常见裁剪或 v1 风格，直接影响资源管理能力。 |
| overlayfs | 联合文件系统，容器镜像分层与写层的实现基础。 | 容器可用性判定项之一；Android 自身用它挂系统分区不等于允许任意使用。 |
| 假 root | proot 内 `uid=0` 但实际仍是应用 UID 的状态。 | 不能 mount/iptables/改内核参数；验收时不能按真 root 承诺。 |
| proot 税 | proot 的 ptrace 路径重写带来的 CPU/I-O 开销（案例实测为单核两成上下，因负载而异）。 | 决定"轻量应用服务器"定位：编译、包管理、重 I/O 会明显变慢。 |

## 4. 遥测桥（Track B）

| 术语（英文） | 一句话定义 | 为何重要 |
|---|---|---|
| 遥测桥（Telemetry Bridge） | 运行在宿主上的只读采集 App，把 App 可访问的宿主状态通过本机 HTTPS 暴露给服务器。 | 解决 proot 读不到电池/WiFi/屏幕等宿主状态的缺口；无 Root 下的推荐方案。 |
| loopback | 仅本机回环可访问的监听方式。 | 桥的安全底线：不得监听局域网/公网。 |
| Bridge token | 服务器与桥之间的本地 API 凭据。 | 最小权限载体；不得给控制面/日志/公网。 |
| 证书 pin（certificate pinning） | 服务器校验桥证书指纹（SHA-256）而非仅信任 CA。 | 防本机伪造服务；MVP 必做，换成 mTLS 前不可省。 |
| mTLS | 双向 TLS，客户端也出示证书。 | 比 token+pin 更强的加固目标，属 Phase 2 增强项。 |
| 配对（pairing） | 一次性交换/确认 token 或证书的流程。 | 决定换机/重装后桥能否安全上线；缺失则只能人工拷贝。 |
| null 语义 | "不可得/无权限/厂商隐藏"用 null 表达，绝不用 0 伪造。 | 防止把"缺数据"误判为"健康数据"，是数据契约的红线。 |
| 新鲜度（staleness） | 数据距采集时间的年龄，超过阈值标记 stale 并回退。 | 防止 UI/控制面使用过期数据做决策。 |
| 能力清单（capabilities） | 桥自报哪些字段在当前设备可得。 | 让上层按能力降级，而不是猜设备。 |
| Bridge fallback | 桥不可用/过期时，服务器回退到 Termux 采集并标注来源。 | 故障隔离的具体实现：桥挂不能拖垮监控。 |

## 5. 控制面与运维

| 术语（英文） | 一句话定义 | 为何重要 |
|---|---|---|
| 控制面（Control Plane） | 面向人的查询/解释/受控操作入口（如 AI 运维助手），不是运行时必需依赖。 | 明确"可挂、可关、不能碰密钥"的边界。 |
| Tier1 / Tier2 / Tier3 | 只读 / 受控写（确认+快照+审计）/ 仅人工 SSH 的三级权限模型。 | 防误操作与提示注入的通用分层；Agent 默认只能 Tier1。 |
| server-ops | 服务器侧受控运维入口，封装状态查询与 Tier2 写操作。 | 把"危险命令"收敛为可审计、可回滚的动作。 |
| 审计日志 | 记录谁在何时做了什么操作的结构化日志（JSONL 等）。 | 事故复盘与合规证据；不允许静默执行写操作。 |
| dry-run | 只展示将要执行的动作而不真正改动。 | Tier2 前的默认姿态，降低误操作成本。 |
| blue-green | 新旧两套入口/目录并行，切换验证后再回滚或保留。 | 升级失败时可在分钟级切回，避免长时间中断。 |
| 看门狗（watchdog） | 周期性检查进程状态与健康端点、失败则重启的守护逻辑。 | 服务自愈的最小实现；比"等人工发现"更能缩短不可用时间。 |
| soak | 持续运行观察窗口（如 24h）用于暴露慢故障。 | 重启/单次健康检查通过 ≠ 稳定；soak 是验收硬门禁。 |
| SLO | 服务目标（可用率、时延、恢复时间等）的可度量承诺。 | 把"感觉稳定"变成可验收指标，避免伪造完成。 |
| RPO / RTO | 恢复点目标（可容忍丢多少数据）/恢复时间目标（多久恢复）。 | 决定备份频率与回滚演练要求。 |
| 回滚（rollback） | 把变更撤回到上一个已知可用状态。 | 没有回滚方案的变更不允许实施。 |
| 快照（snapshot） | 变更前对配置/数据的可恢复副本。 | 回滚的物质基础；"有快照但未演练"仍视为无回滚。 |
| 故障注入 | 主动制造进程退出/断网/权限失效等故障，验证降级与自愈。 | 验证故障隔离是否真的成立，而不是只写在文档里。 |
| 验收证据 | 命令输出、日志、仪表数据等可复核材料。 | 文档声称不算证据；未实测不标完成。 |

## 6. 方法论与流程

| 术语（英文） | 一句话定义 | 为何重要 |
|---|---|---|
| Track A / B / C | A=服务器栈；B=宿主遥测桥；C=两者之间的集成与控制面。 | 三轨职责分离是整套方法论的骨架。 |
| 路线（route） | 改造路线标识：A（Termux+proot 无 Root）、A+（A 的优化档）、B（解锁+Root+chroot）、C（自编译内核/ROM）、D（原生 Linux 移植）。 | 路线选择必须基于探测数据与门禁，不能凭偏好。 |
| device-profile | 设备档案的结构化记录（身份/启动/内核/硬件/存储/加密/特性/约束/未知项）。 | 评估、复现、换机迁移的共同输入；字段名与工具保持一致。 |
| profile 来源 | 档案字段的证据来源：`measured`（实测）/`documented`（文档或社区证据）/`assumed`（默认假设）。 | 区分"确定事实"与"假设"，防止把假设当结论。 |
| case | 一台真实设备的完整改造记录（含证据与偏差），冻结保存，不做美化改写。 | 用来验证方法论、做回归样例、反推新踩坑。 |
| fleet | 多台设备被同一套方法论与工具管理时的集合概念。 | 未来扩展方向；单设备场景不需要它，不能为它过度平台化。 |
| Gate（门禁） | 阶段转出前的强制检查点（如 G-A/G-B0），未通过不得进入下一阶段。 | 把"继续做"变成可判定的规则，避免带病推进。 |
| DoD（完成定义） | 一项任务/阶段被判定完成的验收清单。 | 防止"差不多完成"与伪验收。 |
| assumptions | 评估/计划中显式列出的默认假设（未知时的保守取值）。 | 让后续 Agent 知道哪里需要真机验证，而不是盲目继承。 |
| confidence | 评估结论的置信度（high/medium/low），由字段来源与门禁证据决定。 | 低置信度时应先补探测，不应直接开工。 |
| ID 前缀 | MTH（方法论）/PIT（踩坑）/GRD（护栏）/ADR（决策记录）/REQ（需求卡，可选）/TOOL（工具）/CASE（案例）/BL（待办）。 | 稳定 ID 是可检索、可引用、可去重的基础；编号只增不复用。 |
| ADR（Architecture Decision Record） | 对关键决策的记录：状态、背景、决策、后果（重大决策加备选正反对照）；`superseded` 不删除并回链新 ADR。 | 让后来者知道"为什么这样定"，避免反复争论或误删约束；规则见 [MTH-011](10-document-lifecycle.md) §2.4。 |
| DRI（Directly Responsible Individual） | 结果负责人：对目标、范围、验收和是否交付负责；不是"写代码的人"默认担任。 | 防止"人人负责＝无人负责"；Agent 可整理证据但不能替代决策/验收。 |
| Diátaxis | 文档四象限分类：教程/指南/参考/释义（＋项目记录层），按"教做事还是帮理解"归置。 | 混类（教程里塞参考、复盘里塞规范）是文档腐化主因，发现即拆分+互链。 |
| 阶段门 G0–G7 | 项目/交付治理门：G0 立项/发现、G1 范围/基线、G2 方案、G3 实现/验证、G4 用户验收、G5 发布就绪、G6 发布/观察、G7 复盘/生命周期；每门记 `PASS/FAIL/WAIVED`。 | 与 MTH-003 的 P0–P6、路线门禁 G-A/G-B0/G-L* **并行不替代**；WAIVED 需批准人+到期日。 |
| 风险分级 L/M/H | 按影响缩放的流程档：L=文档/局部脚本；M=新工具子命令/OEM 适配；H=解锁/固件/数据迁移/生产割接/隐私数据。 | 决定最小流程与审批强度；不确定按较高一档，不得因"Agent 能自动做"降级。 |
| 三态退出码 0/3/4 | 证据卡退出码契约：`0=VERIFIED`（本次实跑通过）/`3=SKIPPED`（未验证，**不是通过**）/`4=FAILED`（校验/断言失败；通用脚本非零亦算失败）。 | 防止把"没验证"写成通过；`preflight` 同语义。 |
| 知识债（knowledge debt） | 知识层的欠账：P0 影响正确性（口径漂移/索引缺失）、P1 影响效率（过时/重复）、P2 锦上添花；进 backlog 并给时限。 | 不登记就会"看起来完备、实际空转"；实证缺口必须挂时限。 |
| SBOM（Software Bill of Materials） | 软件物料清单（SPDX/CycloneDX 等格式），列出依赖组件与版本。 | 发布门禁的依赖追溯基础；本仓库当前**未生成**（待落地）。 |
| provenance（制品来源证明） | 记录并（可选）签名证明制品由哪个源提交、依赖与构建流程生成。 | 来源无法确认的二进制不得宣称为官方构建；按风险渐进（本仓库未落地）。 |
| 规范版本 MAJOR/MINOR/PATCH | 协议/规范语义化版本：MAJOR=红线或规则不兼容（必须整改且走 ADR）；MINOR=新增条款；PATCH=澄清。 | 分支须记录遵循版本，跨版本合并前核对差异，防止各分支各自演化。 |
| Agent 回归（AR-01..AR-10） | 针对 Agent 行为的可重复小回归集（红线/幻觉/验收/历史失误样本），对应协议/清单/反例的机检契约。 | "读起来更好了"不是证据；回归 FAIL 不回滚等于没测；不替代任务验收。 |
| preflight | 统一质量门命令：`index → validate --strict → unittest → check-links`，退出码 0/3/4。 | 把"该跑哪些检查"收敛为一个可 CI 消费的入口；有跳过必须申报。 |
| 方法论层（methodology） | 设备无关的规范正文（`methodology/MTH-*.md`）。 | 与案例/工具解耦，换设备不废文档。 |
