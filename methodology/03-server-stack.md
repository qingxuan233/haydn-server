# MTH-004 · 服务器栈（Track A）

> **结论先行**：在**无 Root、BL 锁定**的 Android 手机上，服务器栈的默认实现是
> **Android → Termux:Boot → 启动脚本 → proot 用户态 Linux → supervisord → 服务**。
> 容器与 systemd **不是"没配好"，而是多数手机内核根本不支持**（缺 `USER_NS`/`PID_NS`/cgroup 委派）；先探测再决定，不要反复尝试。
> 服务从**最小核心集**（远程接入 + 入口/TLS + 守护 + 备份）起步，按资源预算逐步增加；网络默认**局域网优先、公网仅受控入口**。

---

## 1. 为什么是 Termux + proot（而不是容器/原生 Linux）

| 候选方案 | 需要的条件 | 本方法论的结论 | 代价/限制 | 何时才考虑 |
|---|---|---|---|---|
| **Termux + proot（A 路线）** | 无需 Root、无需内核命名空间；ptrace 可用 | ✅ **默认方案** | 假 root；不能 mount/iptables；无 systemd；I-O 与包管理明显变慢；`/proc` 部分数据被 Android 替换 | 几乎所有场景 |
| 容器（Docker/Podman） | 内核 `USER_NS`/`PID_NS`/cgroup 委派/overlayfs/netfilter 齐备 | ❌ **默认不可用**；必须真机探测全绿才评估 | 手机内核普遍裁剪；即使能跑也增加复杂度与资源占用 | B 路线且内核探测通过 |
| chroot + 服务管理（B 路线） | Root、解锁、真 rootfs | ⚠️ 非默认；需 P4 门禁与用户授权 | 清数据/失保/完整性风险；OTA 变手动；救砖成本 | 需要真 Linux 能力且用户明确接受代价 |
| 原生 Linux（C/D 路线） | 社区移植或自编译内核 | ❌ 无成熟移植时不推荐 | 人月起工作量；关键驱动最难齐 | 仅研究场景 |
| Termux 原生（无 proot） | 仅 Termux 仓库包 | 可行但生态受限 | 无完整 glibc 生态；服务/依赖选择少 | 极轻量、单服务场景 |

**三条通用结论（设备无关）**

1. proot 的**假 root**决定能力边界：不能改内核参数、不能 mount、不能 iptables；`/proc` 中被 Android 替换的全局统计**不可信**（监控不要依赖它）。
2. proot 的**性能税**决定定位：适合"轻量应用服务器"，编译/包管理/重 I/O 会明显变慢；用离线包与缓存来降低重建时间。
3. **服务守护只能用用户态方案**（supervisord/runit 等）；systemd 需要 PID1 语义与 cgroup 委派，proot 内一般起不全，不要作为验收前提。

> 证据：案例在无 Root 条件下以 proot 方案稳定运行多服务，并明确记录"容器不可用/系统级 `/proc` 不可得"为已知限制（[当前状态](../docs/00-overview/当前状态.md)、[28 全栈规范](../docs/00-overview/28-全栈整体方案规范.md)）。以上是**案例实证**；新设备仍须按 [MTH-002](01-assessment.md) 探测。

## 2. 启动链（必须可复现、可观测、可人工兜底）

```text
电源/开机
  └─ Android 启动完成（BOOT_COMPLETED；FBE 下可能晚于用户解锁）
       └─ Termux:Boot 执行 ~/.termux/boot/ 脚本（按文件名顺序）
            ├─ termux-wake-lock（防休眠杀进程）
            ├─ 启动 Termux 侧远程接入（如 sshd）
            └─ 进入 proot rootfs → supervisord → 各服务（autorestart）
                 └─ 外层 watchdog（周期检查 + 失败重启 + 日志留痕）
```

| 条件 | 为什么必需 | 检查方式 | 未满足的典型表现 |
|---|---|---|---|
| Termux + Termux:Boot 已安装 | 无 Root 下唯一稳定的自启入口 | 重启后 boot 脚本是否执行 | 重启后服务全部消失 |
| 电池优化/后台豁免 | Doze 与 OEM 清理会杀进程 | 系统设置/命令核对白名单 | 几分钟到几小时后整体掉线 |
| 无锁屏凭据或接受人工启动 | FBE：用户解锁前部分目录不可读，`BOOT_COMPLETED` 可能延迟 | 现场确认锁屏策略 | 重启后服务不自动恢复，必须人工开屏 |
| 启动脚本幂等 | 重复执行不得起双份进程 | 重启/重复调用测试 | 端口冲突、双守护互相杀 |
| 双层守护 | 内层 supervisord + 外层 watchdog，覆盖不同故障 | 杀进程后能否自动恢复 | 单点守护被系统杀掉后不再恢复 |
| 日志落盘且轮转 | 否则根因不可见、磁盘会被写满 | 日志目录与大小检查 | 无法复盘、磁盘写满导致服务退出 |
| 三轨独立 | 服务器链失败不得影响遥测桥，反之亦然 | 分别停掉一条链观察 | 级联故障、整机失联 |

**必须**：启动链、服务守护、桥/控制面各自有独立的失败域；启动链失败允许"人工兜底"，但必须在文档中写明该限制，不允许宣称"永远自启"。

## 3. 服务集分层（不绑定具体服务数量）

> 原则：**先最小核心集上线，再按预算增加**。4GB 内存的机器建议 2–3 个服务；8GB 可到 6–8 个轻量服务；任何单个服务的内存/CPU 占用都需要**实测**后再纳入预算（服务数量不是目标，稳定才是）。

| 层 | 职责 | 是否必需 | 典型实现族（示例，不绑定） | 失败影响 | 降级/替代 |
|---|---|---|---|---|---|
| **最小核心：远程接入** | 提供可远程维护的 shell/管理通道 | ✅ 必需 | SSH 服务端；受控隧道客户端 | 无法远程维护，只能现场 | 保持一条受控入口；不要开公网 ADB |
| **最小核心：入口/TLS** | 统一反向代理、TLS 终止、局域网访问 | ✅ 必需 | 反向代理 + 证书 | 应用不可访问 | 直连单个服务（临时）；恢复后切回 |
| **最小核心：守护/自愈** | 拉起与重启服务，保留日志 | ✅ 必需 | supervisord；watchdog 脚本 | 单服务崩溃不恢复 | 外层 watchdog + 人工重启 |
| **最小核心：备份** | 配置/数据定期备份与恢复入口 | ✅ 必需 | 加密备份脚本 + 恢复校验 | 数据丢失不可接受 | 先备份再上线，无例外 |
| 推荐：状态面板/聚合 | 查看服务、磁盘、备份、审计 | 推荐 | 轻量 Web 面板 + 只读 API | 不可观测，排障变慢 | 命令行健康检查 |
| 推荐：文件同步/网盘 | 数据同步与共享 | 推荐（视需求） | 同步服务/WebDAV | 数据不流动 | 备份链兜底 |
| 推荐：监控/指标 | 温度、负载、磁盘、可用率 | 推荐 | 指标采集 + 定时健康检查 | 无法提前预警 | soak/日志巡检 |
| 可选：代码托管/CI 辅助 | 自托管仓库、轻量 runner | 可选 | 轻量 Git 服务 | 无影响 | 关闭释放资源 |
| 可选：下载/定时任务 | 离线下载、cron 类任务 | 可选 | 下载器 + cron | 无影响 | 关闭或错峰 |
| 可选：AI 控制面 | 自然语言查询/受控运维 | 可选 | 控制面进程 + 只读状态 API | 无影响（必须可挂） | 直接命令行运维 |
| 可选：内网工具/DNS | 内网服务发现、工具页 | 可选 | 轻量 DNS/静态页 | 无影响 | 关闭 |

**服务集硬约束**

1. 新增服务前先算公式：`预算内存 ≈ 已用 + 新服务峰值 + 守护/日志/缓存余量`，余量不足不新增。
2. 不跑重数据库/重 JVM/重编译型负载作为常驻服务；确有需求则评估外部机器分担。
3. 每个服务必须有：健康检查方式、日志路径、重启策略、回滚方式、资源实测值。
4. 服务数量增加时优先"合并职责"（例如一个反向代理承载多个应用），而不是无限加进程。
5. 任何服务失败不得导致**备份链**失效；备份是最后防线。

## 4. 网络与暴露面

| 层 | 允许 | 要求 | 检查方式 |
|---|---|---|---|
| 本机回环（loopback） | ✅ 桥/内部 API 只允许本机 | TLS + 凭据 + 证书校验；只读 | 非本机来源不可达；无凭据请求被拒绝 |
| 局域网 | ✅ 默认入口 | TLS 或明确接受明文；固定 IP（DHCP 保留/静态）；只暴露必要服务 | 局域网健康检查；端口清单核对 |
| 受控公网入口 | ⚠️ 仅当用户明确批准且已有受控入口 | 复用现有入口，**不新增暴露**；认证 + 限流 + 审计；地址/凭据不入库 | 入口清单核对；401/403/429 行为验证 |
| 外部服务（异地备份/监控/MFA/隧道等） | ❌ 默认不接 | 用户逐项确认；评估数据去向与密钥管理 | 服务清单与用户授权记录 |
| ADB | 仅维护期 | 用完关闭；不在公网/不受控网络开启 | ADB 状态与授权记录 |

**网络原则（必须）**

1. **局域网优先**：能在内网解决的问题不要拉公网。
2. **单一受控入口**：需要公网时复用既有受控入口，不逐个服务开端口。
3. **凭据不入库**：入口地址、端口、token、证书私钥均属敏感信息（[GRD-006](../guardrails/GRD-006-secret-hygiene.md)）。
4. **IP 漂移**：用 DHCP 保留或静态配置；脚本/文档不得硬编码具体地址，运行期动态获取。
5. **桥只读本机**：遥测桥不得监听局域网/公网（见 [MTH-005](04-telemetry-bridge.md)）。

## 5. 备份与审计

| 项 | 默认要求 | 说明 |
|---|---|---|
| 备份范围 | 服务配置、数据目录、证书/凭据、审计日志、关键脚本 | 配置变更前先快照 |
| 频率 | 每日（可按数据变化加快） | 首版可接受 RPO ≤24h；关键数据应更短 |
| 加密 | 备份包加密；口令与备份包分离存放 | 备份里含凭据，泄露=全面失守 |
| 异地/离线 | 至少一份不在手机本体 | 手机丢失/损坏时仍可恢复 |
| 恢复入口 | 有可执行的恢复命令与校验步骤 | `--verify` 类校验；**恢复未演练 ≙ 无备份** |
| 审计 | 受控写操作、配置变更、备份/恢复均留结构化日志 | JSONL 等；包含时间/动作/结果，不记录密钥值 |
| 保留 | 轮转保留（例如最近 N 份 + 月度一份） | 防止磁盘写满；保留策略写入 runbook |
| RPO/RTO | RPO ≤24h；RTO ≤30 分钟（服务级恢复）；回滚 ≤10 分钟（单变更） | 指标按场景调整，但必须书面化并演练 |

**必须**：备份不可写入仓库（`backup/` 等目录不入库）；备份口令不得出现在文档/日志/聊天；恢复演练必须真实执行一次并留证据。

## 6. 日志与指标

| 类别 | 内容 | 要求 |
|---|---|---|
| 服务日志 | supervisord 日志、各服务 stdout/stderr | 轮转（按大小/日期）；单文件上限；保留窗口明确 |
| 系统/宿主日志 | Android 崩溃、自启、权限重置 | 只读采集；不写敏感信息 |
| 审计日志 | 写操作、备份、恢复、权限变更 | 不可静默；保存期≥备份周期 |
| 指标 | 内存、负载、磁盘水位、温度、可用率、数据新鲜度 | 采集频率与存储量匹配；避免拖垮宿主 |
| 健康检查 | 本机/局域网健康端点 + 进程状态 | 健康端点不得泄露敏感信息 |

**proot 内的指标陷阱（必须记住）**：proot/Android 下部分全局统计（如 `/proc` 中的系统级累计）不可信或是假数据。**优先使用**：服务自身日志、supervisord 状态、宿主遥测桥（App 可访问状态）、外部探测。任何"全局精确 CPU/原始网络字节"承诺在无 Root 时都不可信——缺失就标 `null`，不要伪造。

## 7. 资源预算（按设备档位给区间，非承诺）

| 资源 | 参考预算 | 超限信号 | 处理 |
|---|---|---|---|
| 内存 | 服务 + 守护 + 日志缓存 ≤ 设备可用内存的 60–70% | LMK 杀进程、swap 抖动 | 减服务/降缓存/调守护 |
| CPU | 空载不应持续占满单核；proot 本身有固定开销 | 持续高负载、温度爬升 | 降频/错峰/减少轮询/关非必要服务 |
| 存储 | 数据+日志+备份 ≤ 可用空间 80%；日志必须轮转 | 磁盘水位告警、写入变慢 | 清理/外置/缩短保留 |
| 温度 | 长期运行不触温度墙；电池温度常态可控 | 降频卡顿、充电异常 | 限充/降负载/改善散热/分时任务 |
| 网络 | 上行受限时避免大流量同步/备份集中跑 | 时延抖动、超时 | 错峰、限速、增量同步 |
| proot 税 | 单核固定开销（案例实测随负载变化，约两成上下量级） | 编译/包管理卡顿 | 离线包、缓存、错峰构建 |

**预算规则**：先测后加；每个新服务都要记录"峰值内存/空载 CPU/磁盘增量"；连续三天超限即视为不稳定，必须减负。

## 8. 高层安装步骤（执行细节以案例 runbook 为示例）

> 以下为**设备无关**的高层步骤；具体命令、离线包、代理配置等以已验证案例的 runbook 作为示例参考（**案例实证**）：[17 研究平台环境构建手册](../docs/20-server/17-研究平台环境构建手册.md)、[03 操作手册](../docs/20-server/03-操作手册.md)。新设备必须按 [MTH-002](01-assessment.md) 重新评估，不得照抄机型专属步骤。

1. **宿主基线**：开 USB 调试 → 首次授权 → 安装 Termux/Boot → 白名单与后台豁免 → 记录基线（重启 1 次验证）。
2. **rootfs 准备**：选择离线包或发行版安装方式；慢网络优先离线；记录版本与校验值。
3. **进入 Linux**：准备启动包装脚本（绑定必要目录、工作目录、环境变量）；先验证"能交互执行命令"。
4. **装守护**：安装 supervisord 并定义服务模板（stdout 日志、autorestart、优先级）。
5. **核心服务**：远程接入 + 反向代理/TLS + 最小状态页；每加一个服务就更新资源预算。
6. **自启链**：写 `~/.termux/boot/` 脚本（wake-lock → 进入 Linux → 启动守护）；做幂等与失败兜底。
7. **网络**：固定局域网地址（DHCP 保留/静态）；确认仅必要服务可达；记录入口清单。
8. **备份/审计**：配置加密备份、恢复校验、写操作审计；先做一次恢复演练。
9. **日志/指标**：日志轮转、健康检查、告警阈值；确认采集不会拖垮宿主。
10. **验收**：重启 N 次 + 24h 观察 + 备份恢复 + 局域网访问 + 资源/温度在预算内（见 [MTH-008](07-validation.md)）。

## 9. 验收清单（服务器栈）

- [ ] 重启 N 次（建议 ≥5）后，无需 PC/ADB，核心服务与入口自动恢复
- [ ] 远程接入可用；入口/TLS 在局域网健康检查通过
- [ ] 守护自愈：杀进程后能自动恢复，且日志有记录
- [ ] 备份可用且恢复演练通过（含凭据类文件）
- [ ] 审计日志存在且写操作可追溯
- [ ] 资源占用与温度在预算内；无持续高负载
- [ ] 暴露面仅 loopback/局域网/受控入口；无未授权端口与服务
- [ ] 日志轮转与磁盘水位正常；无敏感值写入日志
- [ ] 启动链失败时，有人工兜底步骤且已写入 runbook

## 10. 常见失败处理

| 症状 | 优先怀疑 | 处理 | 深挖 |
|---|---|---|---|
| 重启后服务全无 | Termux:Boot 未执行 / FBE 锁屏 / 白名单缺失 | 先人工启动验证链，再查自启条件 | [pitfalls/README.md](../pitfalls/README.md) |
| 服务跑了，但几分钟/几小时后消失 | Doze/OEM 清理/内存不足 | 白名单 + wake-lock + 减负 | 同上 |
| proot 启动即崩溃 | 包装脚本绑定了不允许的路径或软链处理异常 | 回退到最小绑定，逐步加目录 | 案例经验矩阵（[17 手册](../docs/20-server/17-研究平台环境构建手册.md)，案例实证） |
| 包管理/安装卡死 | 网络差/源慢/锁未释放 | 离线包/换镜像/清理锁后重试 | 案例经验（同上） |
| 服务启动即退出 | 依赖缺失/目录不存在/权限错误 | 看服务日志定位，补依赖/目录 | 服务日志 |
| 磁盘写满导致服务异常 | 日志/备份无轮转 | 启用轮转+清理；恢复前先备份 | [08 事故复盘](../docs/20-server/08-事故复盘与重置重建报告.md)（案例实证） |
| 局域网突然不可达 | IP 漂移/DHCP 变化 | 固定租约/静态 IP；动态探测地址 | [32 多厂商适配](../docs/10-device/32-多厂商Android适配与迁移指南.md) |
| 温度过高/降频 | 负载超预算/散热差/充电策略 | 降负载、限频可做的项、改善散热 | [06 A+ 优化](../docs/20-server/06-A+优化方案.md) |
