# MTH-008 · 验收与稳定性

> **一句话**：验收不是"写一段完成了"，而是**用可复现的证据证明门禁逐项通过**；稳定性不是"跑了一会儿没挂"，而是**在受控观测窗口内、在禁止变更的前提下，量化可用率与失败模式**。
>
> 铁律：**无证据不宣称完成**；目标值与实测值分开；失败与偏差必须保留记录，不得为了"好看"删除或改写。

## 1. 验收框架

### 1.1 证据类型

| 证据类型 | 形式 | 要求 | 存放 |
|---|---|---|---|
| 命令输出 | 终端文本（脱敏） | 含时间、命令、返回码；可复现 | 案例/证据目录或报告附件 |
| 健康快照 | JSON（API/桥/审计） | 含来源、新鲜度、版本、时间戳 | 随验收报告归档 |
| 日志片段 | 关键日志行 | 含时间与事件；不含凭据 | 随验收报告归档 |
| 审计记录 | 结构化条目 | 能证明"谁在何时做了什么、结果如何" | 服务器审计（只读引用） |
| 时间线记录 | 重启/故障注入时间表 | 每次操作的开始/结束/观察结果 | 验收报告 |
| 截图/录屏 | 可选辅助 | 不能替代命令输出（只作佐证） | 报告附图 |

**证据的脱敏要求**：地址、端口、token、口令、设备序列号、个人数据一律不进入证据；需要引用时写"部署配置中的受控入口"或占位符。

### 1.2 谁验收、何时冻结

| 角色 | 职责 |
|---|---|
| 执行者（人类或 Agent） | 按 SOP 执行、采集证据、如实记录失败 |
| 评审者（Agent 或人类，非执行者） | 核对证据与门禁、抽查复现、判定通过/不通过 |
| 负责人（Lead/维护者） | 冻结结论、决定回滚或放行、更新状态与变更记录 |

**冻结时机**：

- 进入 **24h soak** 前冻结：锁定软件版本、配置、凭据状态；之后**禁止任何变更**（见 §4）。
- 冻结期间发现的失败只记录、不修复；修复需退出 soak 窗口，重新起算。
- 结论冻结后：更新权威状态文件 + [CHANGELOG](../CHANGELOG.md) + 案例记录；后续变更必须重新过对应门禁。

## 2. 验收门禁表

| 门禁 | 标准 | 证据 | 失败处置 |
|---|---|---|---|
| **G0 构建可装** | 从干净环境按脚本可重复构建；产物可安装、版本号正确 | 构建日志 + 产物校验 + 安装输出 | 不进入后续门禁；修构建链 |
| **G1 重启自启 5/5** | 连续 5 次重启，目标组件均自动就绪 | 5 行重启记录表 + 每次健康输出 | 记录失败原因；OEM profile 修正后重跑 5 次 |
| **G2 数据完整/null 语义** | 主字段非空或**明确 null**；无伪造 0；来源标记正确 | 状态快照 + 字段逐项核对表 | 修正采集/契约；重跑 |
| **G3 回退** | 目标组件不可用时自动降级并标注来源；恢复后回到正常来源 | 注入记录 + 前后快照 | 修降级逻辑；不得留"假数据" |
| **G4 安全** | 未授权 401、非 loopback 不可达、pin 反例失败、无明文凭据 | 安全清单逐项输出 | 硬失败；修复后重测 |
| **G5 24h soak** | 观测窗口 ≥24h；可用率 ≥99%；无崩溃循环、无假数据、无异常回退潮 | soak JSONL + 汇总统计 + 失败事件表 | 失败即记录并重新起算；不得缩短窗口 |
| **G6 故障注入** | 注入矩阵每项：预期行为出现、降级正确、恢复正确、无级联 | 注入矩阵记录表 | 修容错；失败项单独重跑 |
| **G7 恢复演练** | 备份 → 受控破坏 → 恢复 → 校验，闭环通过 | 演练时间线 + 校验输出 | 视为"没有回滚"（[GRD-004](../guardrails/GRD-004-backup-before-change.md)）；修备份/恢复流程 |
| **G8 升级/回滚** | 升级后功能与数据保持；回滚后可回到上一版本并验证 | 升级/回滚记录 + 版本证据 | 保留旧版本与备份；重新演练 |

> **命名说明**：本文 G0–G8 是**验收项编号**；[MTH-003](02-roadmap.md) 的**阶段转出门禁**（G-A/G-HOST/G-CORE/G-BRIDGE/G-OPT/G-SOAK/G-REL）是另一命名空间。阶段门禁可引用本文验收项作为证据，但不得把两者当同一编号。

> 门禁定义可扩展，但**不得删除已通过项**；新增门禁必须有可执行标准与证据要求。

## 3. 5 次重启 SOP

**前置**：

- 指定不变更窗口；关闭自动更新/自动清理；确认维护通道可用；记录当前版本与关键配置 hash。
- 若是 OEM 首次验证，先完成该 OEM profile 的自启/省电/后台白名单设置（步骤见案例层与 [MTH-002](01-assessment.md)）。

**每次重启的固定动作**：

1. 重启前：记录时间、当前版本/配置、当前健康状态。
2. 重启：使用受控方式（正常重启；必要时人工按键，不使用危险命令）。
3. 等待预期就绪窗口（给足系统启动 + 服务启动时间；观察期要大于历史基线）。
4. 检查：目标组件进程/服务状态、健康端点、数据来源标记、聚合 API、控制面可用性、数据字段完整性。
5. 记录：一行一条（次数/时间/就绪耗时/各项结果/异常现象）→ 归档为证据。
6. 判定：5/5 全部通过才算 G1 通过；任何一次失败都要记录原因并归零重跑（不允许"跳过失败的那次"）。

**重启记录表模板**：

| 次 | 开始时间 | 组件就绪 | 健康 | 来源标记 | 数据完整 | 控制面 | 耗时 | 异常 |
|---|---|---|---|---|---|---|---|---|
| 1 | | | | | | | | |
| … | | | | | | | | |

**失败处理**：

- 先看系统侧（服务是否 running、通知/前台服务是否可见、是否有厂商清理），再看应用侧（启动日志、类型声明/权限）。
- 归因到 OEM 行为 → 更新案例层 OEM profile；归因到代码/契约 → 修复后重跑全 5 次。
- **不得**用"手动打开一次 App"掩盖自启失败；那证明的是手动路径，不是自启。

## 4. 24h soak SOP

**目标**：证明在**无人工干预、无变更**的连续窗口内，系统可用性与数据质量达到目标。

**观测项与频率**：

| 观测项 | 建议频率 | 记录字段 |
|---|---|---|
| 桥健康（无 token 端点） | 60s 级 | ts, ok, latency_ms |
| 桥状态（带 token 端点） | 60s 级 | ts, ok, schema, version, age_s |
| 聚合 API 来源/新鲜度 | 60s 级 | ts, source, age_s, error, capabilities |
| 服务状态（数量/关键服务） | 5min 级 | ts, 期望数, 实际数, 非 RUNNING 列表 |
| 控制面入口 | 5min 级 | ts, 状态码/可用性 |
| 宿主资源（磁盘/内存/温度） | 5min 级 | ts, 关键指标 |
| 失败事件 | 事件驱动 | ts, 类型, 持续时间, 恢复方式 |

**成功标准**：

- 观测窗口 **≥24h** 连续；可用率 **≥99%**（按采样点计算，失败定义与统计口径必须写进报告）。
- 无崩溃循环（同一组件反复重启）、无数据伪造（字段缺失必须 null + 来源标注）。
- 回退事件可解释（每次降级都有原因与恢复记录）。
- 观测期间**无变更**：不改配置、不升级、不做 Tier2 写、不清理/debloat、不插拔重启（计划内重启需单独标记并从统计中单独说明）。

**记录格式**：优先 **JSONL**（一行一个采样，字段稳定），另附生成汇总（总采样、失败采样、可用率、最长连续失败、失败事件表）。建议使用 [toolkit/termux/soak.sh](../toolkit/termux/soak.sh) 采集与汇总；健康快速检查用 [toolkit/termux/healthcheck.sh](../toolkit/termux/healthcheck.sh)。

**期间禁令**：

- 禁止任何变更（含"顺手优化"、重启服务、改配置、升级 APK）。
- 禁止删除/编辑已有日志与审计；禁止用人工打开 App 等方式"救场"。
- 中断（重启/断电/断网）必须记录；中断超过阈值或无法解释的长时间不可用 → 判定失败，重新起算。

**soak 报告最小字段**：起止时间、版本与配置 fingerprint、采样口径、可用率、失败事件表、回退统计、资源趋势、结论（通过/不通过/部分通过）、证据路径。

## 5. 故障注入矩阵

> 注入原则：**受控、可恢复、可解释**；每次只注入一个故障，记录前后状态；注入后必须恢复并复验。不得在 soak 窗口内注入。

| # | 注入 | 预期行为 | 必须验证 | 恢复方式 |
|---|---|---|---|---|
| F1 | 桥进程被杀/强制停止 | 聚合层降级，来源标非桥；Console/控制面解释原因 | 降级时延、来源标记、无假数据 | 重新拉起（等待自启/维护通道） |
| F2 | 断网（宿主网络断开） | 桥/聚合不可达；本地服务继续；恢复后自愈 | 网络恢复后数据回正、缓存不污染 | 恢复网络，等待重连 |
| F3 | 桥返回 401（token 失效） | 客户端硬失败并降级；错误明确；不重试风暴 | 401 处理、错误日志脱敏、降级来源 | 维护窗口重新配对/轮换 |
| F4 | 桥超时/慢响应 | 客户端超时后降级；有缓存则用缓存并标 stale | 超时阈值、缓存语义、无阻塞 | 结束注入后恢复 |
| F5 | 服务器重启 | 自启链恢复；服务全量 RUNNING；数据继续 | 就绪时间窗、服务计数、桥仍运行 | 受控重启 |
| F6 | 控制面重启/宕机 | 数据面不受影响；控制面恢复后可用 | 隔离性、恢复后登录/状态 | 等待看门狗恢复或人工重启 |
| F7 | APK 升级（同签名原地） | 升级后版本变化、token/权限保留、服务继续 | 升级前后版本/token/数据连续性 | 旧版 APK 回滚 |
| F8 | APK 回滚 | 回滚到旧版可用；配置兼容 | 回滚后健康与来源标记 | 重新升回或保持旧版 |
| F9 | 证书失效/不匹配 | 客户端硬失败并降级；不跳过校验 | 反例测试、错误分类 | 维护窗口修复 pin/证书 |
| F10 | 磁盘将满 | 告警；日志/备份受限；核心服务不崩 | 水位告警、写失败处理、审计不受损 | 清理（受控）或扩容 |
| F11 | 单服务崩溃 | 看门狗/自动重启或人工恢复；不级联 | 重启次数上限、熔断、审计留痕 | 按看门狗策略；超限人工 |
| F12 | 看门狗误动作 | 不重启隔离性服务；有退避与上限 | 熔断行为、人工旁路可用 | 停用自动动作，人工排查 |

**判定**：每项注入都要有"预期 → 实际 → 差异 → 处置"四段记录；差异必须解释，不能只写"正常"。

## 6. 恢复演练

**演练闭环**：`备份 → 校验备份可用 → 受控破坏 → 恢复 → 校验 → 记录`。

**破坏选择（受控）**：

- 优先在**副本/测试实例**上破坏（单服务配置、单数据副本、单凭据副本）。
- 若必须在生产上演练：只破坏**可重建的单点**（如单服务配置），演练前确认备份新鲜且已验证，演练窗口内禁止其他变更。
- **禁止**为演练执行不可逆操作（清数据、删全量备份、刷机、卸载系统包）。

**校验清单**：

- [ ] 服务恢复：期望服务数/关键服务全部就绪。
- [ ] 数据恢复：关键数据可读、抽样比对一致、无空壳。
- [ ] 凭据恢复：认证可用（不是"跳过认证"）。
- [ ] 审计连续：演练动作与恢复动作都有记录。
- [ ] 结论：恢复耗时 ≤ 目标时限；未达标记偏偏差与改进项。

**频率**：首次验收必须做一次；重大变更（升级/迁移/备份策略变更）后重做；平时按季度抽检（可只做副本演练）。

## 7. 经验阈值（目标值，非实测值）

| 指标 | 目标/建议 | 说明 |
|---|---|---|
| 数据新鲜度 | ≤30s 视为新鲜；>120s 回退 | 由聚合层统一定义与展示 |
| 桥 24h 可用率 | ≥99% | 统计口径必须在报告中写清 |
| 服务器重启后全服务就绪 | ≤120s（按设备/服务数调整） | 目标值；实际基线见案例记录 |
| 桥资源占用 | 内存 <30MB；空闲 CPU <1% | 目标值；以实测为准，不达标不等于失败但要记录 |
| 回滚时限 | ≤10min | 升级/配置回滚 |
| 单点恢复（服务级） | 分钟级 | 看门狗/人工恢复 |
| 证据齐全度 | 门禁每项至少 1 条可复现证据 | 无证据 = 未通过 |

> **目标值 vs 实测值**：本文只给目标；实际达成情况必须引用案例层与验收报告（例如 [cases/haydn-k40pro/README.md](../cases/haydn-k40pro/README.md) 与其验收记录、[docs/33](../docs/50-bridge/33-Android-Bridge-MVP实施记录.md) 的阶段性记录）。**禁止把目标值写成"已实测"**。

## 8. 验收报告模板

```text
# 验收报告 <组件/版本>
- 窗口：<开始> ~ <结束>（时区）
- 版本/配置 fingerprint：<版本号 + 配置 hash>
- 执行者/评审者：<角色，不含个人信息>
- 门禁结果：G0..G8 <通过/不通过/未执行 + 一句理由>
- 证据清单：<相对路径/审计条目引用>
- 失败事件表：<时间/现象/处置/是否复发>
- 结论：<通过 / 部分通过（列缺口） / 不通过>
- 未完成项与下一步：<backlog ID 或人工事项>
```

**归档约定**：证据放案例层（`cases/<codename>/`）或其引用的既有记录；新层文档不复制大段原始日志，只给链接与摘要。

## 9. 失败处理与禁止事项

**允许**：退出验收窗口 → 定位根因 → 修复 → 重新冻结 → 重新起算；如实记录失败。

**禁止**：

- 缩短 soak 窗口、跳过采样、只挑"好"的时段。
- 把未跑的门禁标"通过"；把"应该没问题"当结论。
- 删除/改写失败记录与偏差；把目标值当成实测值。
- 在 soak 期间"顺手"变更或人工干预掩盖问题。
- 用截图代替命令证据、用文档声称代替实测。
