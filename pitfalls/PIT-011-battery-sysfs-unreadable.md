## 症状

- shell/App 读取电池 sysfs 被拒（Permission denied），充电上限/旁路等节点不存在或不可写；无法用脚本把充电限制在 60–80%。
- 只能依赖厂商设置里的“充电保护/智能充电/夜间充电优化”开关，不同 ROM 名称与能力不同，有的机型没有。
- 设备长期插电保持 100% 且温度偏高，数月后容量明显衰减，存在鼓包/安全风险。
- 脚本里的限充逻辑“静默失败”（命令返回非 0 或权限拒绝但被忽略），运维者误以为已生效。

## 触发场景

- 把手机当 7×24 常驻服务器，长期插电、满电运行；
- 无 Root，却照抄“用 ACC/写 charge_control_limit 限充”的教程；
- 只按某个机型的经验配置，未在本机验证节点权限；
- 放置环境不通风、被覆盖或靠近热源。

## 根因

- 电池/充电控制节点属特权 sysfs，普通 shell 无读写权限；无 Root 不可用，这是平台硬边界。
- 厂商充电保护是私有 UI 行为（部分机型为硬件旁路），没有统一 API，无法可靠脚本化。
- 锂电池长期满电 + 高温会加速老化与产气，属于硬件层风险；软件侧规避能力有限，必须配合物理措施与监控。
- “静默失败”源于脚本未检查返回码与权限，把不可得当成已完成。

## 规避与修复

1. 先只读探测：检查电池/充电相关 sysfs 节点是否存在、是否可读写，结果写入设备能力矩阵；不假设、不照抄。
2. 无 Root 时的唯一可控项：人工开启厂商“充电保护/智能充电”并记录菜单路径与固件版本；用充电曲线确认是否真的限充。
3. 物理侧同时做：通风、金属支架/小风扇、远离热源、不覆盖；这是零成本且最有效的措施。
4. 监控电池温度/电量/充电状态趋势，设阈值告警；定期检查外观（鼓包立即停用并更换电池）。
5. 禁止写“模拟限充”脚本：无权限写入必须返回明确失败；脚本不得静默忽略错误。
6. 若未来有 Root，再评估 `charge_control_limit` 等节点（仍需实测存在性与机型兼容），并纳入维护窗口。
7. 把“长期插电风险”写进风险登记册与验收标准（电池温度、健康度、外观巡检周期）。

## 验证

- 能力探测输出明确 sysfs 可读/可写状态；限充脚本在无权限时退出码非 0 并报告“不可用”。
- 厂商充电保护开启后，电量在设定上限附近停止上升（记录充电曲线与时间点）。
- 温度与健康趋势有记录；阈值告警可触发；外观巡检表已执行。
- 验收不宣称“已实现脚本限充”，只声明“厂商 UI + 物理 + 监控”。
