## 症状

- 按既定计划推进到解锁阶段时发现官方入口不可用：厂商社区 App 无解锁入口、资格不满足或区域限制，解锁决策门（Gate B0）失败。
- 依赖 Root 的路线（chroot、特权遥测、部分系统优化、容器试验）全部无法执行；若没有替代路线，前期规划与物料投入返工。
- 社区/灰产出现“付费解锁/漏洞解锁”广告，风险与诈骗高发，容易把工程问题变成安全事故。
- 项目文档里仍留着“以后 Root 再做”的承诺，接手者重复尝试。

## 触发场景

- 设备为国行/运营商定制 ROM，厂商官方解锁通道关闭或收紧；
- 账号资格、绑定时长、社区等级等门槛不满足；
- 在未验证解锁可行性的情况下，先做备份/清数据/购买物料等破坏性或不可逆准备；
- 把 Root 当作路线默认前提，没有 fallback 计划。

## 根因

- 解锁是厂商政策与云侧资格判定，不是本地可配置项；不同区域/ROM/批次政策不同且会变化。
- 非官方解锁涉及漏洞利用与灰产，代价（变砖、失保、被植入、法律风险）远高于收益。
- 路线规划若把 Root 设为默认前提而不设决策门，就会在政策变化时整体返工。
- 政策结论有时效性：今天不可用不代表永远不可用，反之亦然；必须以申请时的官方入口为准。

## 规避与修复

1. 设硬性决策门：在**任何破坏性操作之前**验证官方解锁入口是否可用、资格是否满足，并记录日期与证据。
2. 门禁失败立即转 A/A+（无 Root）并冻结 Root 相关计划；不做非官方解锁、不购买第三方解锁服务。
3. 明确能力边界：无 Root 下不承诺 chroot/容器/特权遥测；需要这些能力时考虑换机，而不是硬刷本机。
4. 未来换机按准入清单选机（可解锁、社区与 Root 方案成熟、内核能力可实测、可救砖），不按品牌/型号猜测。
5. 把政策不确定性写进风险登记册与决策记录，标注“以申请时厂商政策为准”，避免下一次会话重复尝试。
6. 保留 Gate 结论与证据链接，项目文档统一改成“当前路线为无 Root”，不再保留模糊承诺。

## 验证

- Gate B0 结论有明确日期、证据来源与“通过/失败”判定，且发生在任何清数据/刷机动作之前。
- 门禁失败后无任何解锁/刷机行为；设备启动链状态保持原样（未解锁、校验完整）。
- 替代路线 A/A+ 完成基线可用：服务自启、遥测、备份等核心能力就绪。
- 换机评审时能引用本条目，先做解锁可行性验证再谈 Root。
