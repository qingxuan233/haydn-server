## 症状

- 开机或故障时看门狗把“正在启动”误判为“已失败”，反复重启目标服务；日志出现连续 restart，服务始终起不来。
- 重启风暴：看门狗重启服务 → 服务启动期间更不可用 → 再次判定失败 → 无限循环；依赖该服务的 token/会话频繁失效。
- 看门狗自身被清理/崩溃后无人拉起；或看门狗与被监护服务互相重启。
- 观测数据被重启风暴污染，无法判断是服务故障还是看门狗策略问题。

## 触发场景

- 健康检查不区分 STARTING/BACKOFF 等中间状态；
- 阈值过于敏感（单次失败即重启）、间隔过短、无退避；
- 看门狗与被监护进程同生命周期，或没有上层托管；
- 维护窗口/批量重启期间仍自动恢复；
- 只做“能重启”的演示，未做故障注入与长时间观察。

## 根因

- 把“进程状态”和“HTTP 健康”混为一谈：启动阶段请求必然失败，被计入连续失败。
- 没有指数退避、有界重启与熔断，故障时行为从“自愈”退化为“风暴”。
- 看门狗没有独立于被监护对象的部署与观测，无法保证自身可用。
- 缺少人工维护开关与告警升级，机器一直尝试而不是交给人处理。

## 规避与修复

1. 状态机：仅在目标服务处于 RUNNING 时才做 HTTP 健康检查；STARTING/BACKOFF 阶段清零计数、不重启。
2. 连续 N 次失败 + 指数退避（带最大间隔）；重启成功后计数清零。
3. 有界重启：时间窗口内最大重启次数，超限即熔断 → 告警 → 等待人工，不再自动重启。
4. 独立性：看门狗由上层监督者托管，且不得重启自身或其父进程；避免自我级联。
5. 观测与审计：记录每次检查/失败/重启/熔断，输出指标与日志，保证自愈过程可观察。
6. 人工通道：维护模式暂停自动恢复；提供手动重启/停止入口并写审计。
7. 故障注入验证四场景：启动中、连续失败、看门狗被杀、服务正常时误报。

## 验证

- 模拟服务启动慢：看门狗不重启，服务最终 RUNNING。
- 连续失败：出现退避、有界重启与熔断告警，而不是无限循环。
- 杀掉看门狗：上层监督者能拉起，且不会引发目标服务风暴。
- 正常服务：无误报/无多余重启；24h 观察无重启风暴，日志可解释每次动作。
